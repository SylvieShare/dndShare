# Сопровождение wiki

Wiki помогает выбрать место изменения, понять контракт и выполнить нужные
проверки. Основные требования к актуальности и выпуску задаёт
[README репозитория](../README.md#документация-и-wiki).

## Приоритет и границы

[README](../README.md) задаёт общие обязательные правила. Тематическая страница
владеет контрактом своей области, а [маршруты](README.md#с-чего-начать) определяют,
что прочитать в начале задачи. Обзор не дублирует подробную инструкцию.
При расхождении описаний проверить их основной источник и исправить противоречие;
не собирать собственный компромисс из старого отчёта и нового контракта.
Существующая ошибка кода не отменяет требование. Фактические версии и лимиты
сверяют с кодом/конфигурацией, требуемое поведение — с текущим контрактом задачи.

Исторический отчёт фиксирует результат на дату/commit и не выдаёт разрешения
на будущие действия. План не доказывает наличие реализации. Параметры и
исключения журнала конкретной модели применяются только к указанной модели;
общие нормы остаются в пайплайне.

## Где описывать тему

| Тема | Основное описание |
| --- | --- |
| Обязательные проектные инструкции | README репозитория; AGENTS.md и CLAUDE.md направляют к нему. |
| Общая архитектура и путь данных | architecture.md и обзор frontend.md. |
| Правила Go, DTO, auth и routes | backend.md; SQL и миграции — database.md. |
| Обязательные проверки | Только матрица testing.md; README и deploy.md ссылаются на неё. |
| Выбор общего UI-примитива | frontend/components.md; токены — css-variables.md. |
| Поведение фичи, права и ограничения | Страница в features/ и её тематические подразделы. |
| HTTP-запрос, DTO и статус ответа | Тематическая страница api/. |
| Таблица, JSON-хранение и миграция | Тематическая страница database/. |
| Установка и художественные правила медиа | handbook-media.md, handbook-art-style.md и mascot.md. |
| Обработка 3D-моделей | Общий процесс — [инструкция](features/maps-model-pipeline.md); индивидуальные рецепты, параметры и результаты — [журнал](features/maps-model-log.md). |
| Измерения и аудит каталога | Датированный отчёт с областью проверки и ссылкой на артефакты. |
| Предложение, ещё не реализованное решение | plans/ в корне репозитория. |

Разные уровни могут описывать одну фичу: страница фичи объясняет её поведение,
API — HTTP-контракт, БД — хранение. Подробности одного уровня должны иметь одно
основное описание; соседние страницы связываются ссылками. Общая таблица
компонентов помогает выбрать примитив; подробная предметная композиция остаётся
рядом с фичей или в frontend/catalogue-components.md.

## Устройство страниц

Обзорная страница отвечает на вопрос «с чего начать» и содержит ссылки на
тематические страницы. Прежние пути frontend.md, api.md, database.md,
features/character-editor.md и features/sessions.md сохраняются как точки входа.

Тематическая страница начинается с назначения. Далее размещаются применимые
разделы: поведение и права, контракт и реализация, ограничения, проверки,
связанные страницы. Не добавлять пустые разделы ради одинакового шаблона.

Заголовки должны отвечать содержанию: загрузка листа не является подразделом
тестов, а частное исправление данных не должно предшествовать устройству БД.
Новую информацию размещают в нужном разделе. Описание недавней правки
переформулируют как текущее поведение вместо добавления очередного абзаца в конец.

Основной тип страницы обозначается в начале там, где его легко перепутать:
«действующий контракт», «обязательные правила», «журнал модели», «исторический
отчёт» или «предложение». У отчёта обязательны границы среза, метод и дата/commit.
Не ставить сегодняшнюю дату вместо неизвестной даты старого измерения.

Изменяемый факт имеет один основной источник:

| Факт | Источник |
| --- | --- |
| Go/toolchain и библиотеки frontend | [go.mod](../go.mod), [package.json](../frontend/package.json), lock-файл. |
| Лимиты production-сборки | [bundle-budgets.json](../frontend/scripts/bundle-budgets.json). |
| Версия обучения | [tutorialIdentity.js](../frontend/src/features/tutorials/lib/tutorialIdentity.js). |
| Хост и механика deploy | [deploy.sh](../deploy/deploy.sh), unit и [runbook](deploy.md). |
| Текущие UUID, SHA и публикация медиа | Свежий MCP-реестр; журналы фиксируют конкретные операции. |

В текущем контракте описывать правило и ссылку на источник. Числа прошлых
запусков и причины изменения лимита помещать в отчёт.

Размер — сигнал к проверке структуры. Обычно тему удобно читать в пределах
150–450 строк; страница длиннее 600 строк требует оценки разбиения по
ответственности. Самостоятельные небольшие контракты могут быть короче.
Оглавление и ссылки должны позволять найти подробности без чтения всех соседних
страниц. Журналы делят на предметные семьи и целые записи моделей, а не по
произвольному числу строк. Большая таблица не оправдывает обзор на сотни тысяч
символов: оставить в нём индекс, записи вынести в тематические страницы.

Раздел «Связанные страницы» завершает документ. Новое поведение вставляют в
нужный раздел перед ним; хронологические дополнения идут в reports. При переносе
сохранить текст целых смысловых блоков, перенести относительные ссылки и обновить
входящие якоря. Проверить, что записи моделей и параметры не потерялись.

## Ссылки и навигация

- Новая основная тема добавляется в оглавление wiki; подраздел — в обзор своей
  области. Каждая страница содержит обратную ссылку.
- Для перехода к странице или разделу использовать относительную Markdown-ссылку.
  Встроенный код подходит для имени поля, функции или команды, но не заменяет ссылку.
- При переносе раздела обновлять ссылки с якорем на его прежнее расположение.
- Конкретные пути к исходникам проверять при переименовании или удалении файла.
  Путь должен указывать на существующий файл; пример нового компонента явно
  обозначается как предложение и хранится в plans/.

## Аудиты и история

У аудита указываются дата или commit, область выборки и метод проверки. Его числа
относятся к этому срезу. Последующие пакеты должны иметь свои границы проверки;
старый аудит нельзя выдавать за live-состояние каталога.

Исторические измерения хранятся в reports/ внутри wiki и ссылаются на текущий
контракт. Предложения из аудитов находятся в plans/ репозитория. Ограничения
реализованной фичи остаются на странице фичи, где проверяются вместе с кодом.
Не переносить полезные ограничения в архив только из-за даты их первого описания.

## Проверка изменения

Из корня репозитория:

    python3 scripts/check-wiki.py --strict

Проверка использует Python 3 без дополнительных зависимостей. Она проверяет
локальные Markdown-ссылки, якоря, HTML-ссылки на изображения, явно указанные
пути к файлам реализации и достижимость страниц из оглавления. Внешние URL и
соответствие описанных механик коду требуют отдельной содержательной проверки.
Структурные предупреждения включают текст после завершающих ссылок, чрезмерный
размер, немаркированные отчёты и датированные журнальные разделы в текущем
контракте. Без `--strict` это предупреждения; с ним они блокируют проверку.
`scripts/test.py` использует строгий режим. Исключения для указателей отчётов
и явно помеченных журналов не превращают их в общие инструкции.

Перед завершением правки:

1. Найти связанные страницы фичи, API, БД и обучения.
2. Обновить основное описание и ссылки; проверить права, ошибки и ограничения.
3. Запустить проверку wiki и посмотреть получившуюся структуру заголовков.
4. Выполнить проверки реализации, предусмотренные README и страницей фичи.
