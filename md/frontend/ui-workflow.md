# Работа над общим UI

Один небольшой вертикальный участок выполняется сразу в вебе и Android.
До реализации записать ожидаемое поведение и границы: состояния, три композиции
окна, доступные действия и критерии завершения. Общие величины принадлежат
[токенам](../../design/README.md), примитивы — своим библиотекам.

**Полный набор запускается только по прямой команде пользователя.** Флаг `--full`
фиксирует такой выбор для человека и CI; сам по себе он не разрешает агенту
запускать широкий набор. Правка, подготовка выпуска и рекомендация инструмента
не заменяют прямую команду пользователя.

## Рабочая копия и кандидат

Новая задача с кодом получает отдельную ветку/worktree на C. Параллельные чаты
не делят рабочее дерево и staging area. Установленные инструменты не копируются:
локальные пути — в игнорируемом `build/dev-tools/local-tools.json`.
Первый запуск в новом worktree автоматически наследует конфигурацию инструментов
основной копии, меняя только поле `source`; повторная установка не требуется.

```bash
python3 scripts/ui.py doctor --emulator emulator-5554
python3 scripts/ui.py pin
```

`pin` фиксирует хеш текущих исходников изолированного worktree **на месте**,
сохраняя Node/Gradle-кеши и сборочные результаты. После изменений кандидат
обновляется повторным `pin`, без нового полного копирования. Во время проверки
исходники кандидата не редактируются; fingerprint проверяется до и после.
Первичный общий checkout для `pin` запрещён.
`prepare` остаётся отдельным экспортом неизменяемого среза для выпуска или
исторического сравнения; создавать его после каждой мелкой правки не требуется.

## Короткий цикл

```bash
python3 scripts/ui.py focus webunit --workspace "$UI_WORKSPACE" --file src/features/handbook/pages/ViewHandbook.test.js
python3 scripts/ui.py focus browser --workspace "$UI_WORKSPACE" --project ui --file tests/tutorials/morph-tiles.spec.js --grep 'shared morph heading'
python3 scripts/ui.py focus native --workspace "$UI_WORKSPACE" --target Test
python3 scripts/ui.py focus native --workspace "$UI_WORKSPACE" --target DeviceTest --test-class ru.dndshare.client.SheetPagerStateTest --emulator emulator-5554
python3 scripts/ui.py focus tools --workspace "$UI_WORKSPACE" --area dev
python3 scripts/ui.py review --workspace "$UI_WORKSPACE" --scenario form-lifecycle --emulator emulator-5554
```

`$UI_WORKSPACE` — абсолютный путь текущего pinned worktree. Web-проверки требуют
явные файлы; без них широкий запуск отвергается до старта окружения.
Нативный Test/All/DeviceTest проверяет выбранный Android-модуль. Выбираются
проверки затронутого поведения, сохранности данных, обучения и ошибок.
Сбой прекращает scoped-план: не тратить время на неотносящиеся этапы.

Отдельный демонстрационный экран использует реальные компоненты с фиктивными
данными без входа и API. Для геометрии/анимации сначала нужен такой короткий
component-тест; интеграция запускается после него. Тест вмешивается в анимацию
по наблюдаемому кадру, а не надеется поймать краткий интервал внешним polling.

Smoke APK обращается к постоянному loopback-порту устройства; `adb reverse`
связывает его со случайным портом тестового Go API. Сборочный ключ учитывает
входы Android, инструменты/SDK и адрес. APK с проверенной контрольной суммой
переиспользуется, пока входы не изменились. Результаты тестов не кешируются.
Gradle build/incremental-кеши сохраняются; runner не удаляет их перед каждым этапом.

## Окружение и изоляция

Автотестовый AVD запускается с `-no-window`, аппаратным `auto/host` при доступном
GPU и рабочим гипервизором. `doctor` записывает фактический renderer Android,
задержку ADB, доступную RAM и нагрузку CPU хоста. Программный renderer и низкая
память дают диагностические предупреждения; неответивший ADB и видимый
автоматический AVD останавливают запуск. Для намеренной ручной сессии есть
`--allow-visible-emulator`. Память/ядра увеличивают по замеру свободных ресурсов.
Физический телефон не выбирается вместо эмулятора.

Один Git common-dir координирует worktrees: блокировка эмулятора берётся только
на действия устройства; обычные unit/build этапы её не удерживают.
Native-компиляции идут через отдельную очередь/lock. Сборка и UI-действия не
меняют чужой ADB server. Модели, production-аккаунты и телефон не являются
тестовыми фикстурами. Артефакты/установки остаются на C; горячие Linux-кеши
Vite/PostgreSQL используют temp из-за семантики Windows/WSL.

## Разбор сбоев и завершение

После двух одинаковых неудач собирать минимальный репро, журнал и состояние
до/после проблемного перехода. Не повторять весь набор в надежде на успех.
Known failures из `scripts/dev/known-failures.json` имеют точный сценарий,
ответственную область, исходный SHA, причину и дату пересмотра. Это аннотации,
а не автоматические skip/зелёные статусы. Новую регрессию проверять отдельно от
воспроизводимого сбоя базового main.

Квитанции `build/ui-runs/` хранят PID/идентичность процесса, heartbeat, этапы,
source hash и exit codes. `ui.py status --run /absolute/run` показывает погибший
runner как interrupted; старый running не считается живой или успешной проверкой.
Нулевое число реально выполненных instrumentation-кейсов — ошибка.

Когда согласованные состояния и проверки прошли, код кандидата фиксируется.
Следующие улучшения отправляются в отдельный этап, а не перезапускают приёмку.
Тесты неизменённых входов можно наследовать только с явным сравнением хешей.
Выпуск — из чистого точного commit с проверкой readiness; APK обновляется через
`install -r`, с сохранением подписи/данных. Полный набор не становится обязательным
из-за самого факта выпуска.

## Парное сравнение

```bash
python3 scripts/ui.py review --workspace "$UI_WORKSPACE" --state sheet-stats --state sheet-stat-editor --emulator emulator-5554
```

Проверяются выбранные состояния в трёх форматах (390×900, 834×1100, 1920×1000),
на одинаковой фикстуре и реальном изолированном Go API/PostgreSQL.
`--scenario form-lifecycle` проверяет только сохранённый ввод/resize/завершение
процесса/конфликт, не запускает браузер и весь обход справочника.

Полный парный набор из 48 снимков и `verify --full` разрешены только прямой
командой пользователя. Полнота ограниченного отчёта считается относительно
заявленных состояний; он не выдаётся за полную матрицу. Новый отчёт не наследует
неполные снимки прошлого запуска. Визуальную приёмку выполняет пользователь;
различия заранее согласуются и фиксируются в
[реестре](../../design/visual-exceptions.json).
