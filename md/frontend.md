# Frontend

Актуальная реализация — Vue 3, Composition API, Pinia, vue-router и Vite 8 в
`frontend/`. Старого Vue CLI, webpack, Axios и серверных JSON-шаблонов листа в
проекте нет.

## Запуск и проверка

```bash
cd frontend
npm install
npm run dev
npm test -- --run
npm run build
```

Vite работает на `:5173` и проксирует `/api` и `/mcp` в Go-приложение на
`:8080`. Production-сборка попадает в `frontend/target/dist`; Go-бэкенд вшивает
её в бинарь. Для неизвестного клиентского пути Go возвращает `index.html`, а
`/api/**` и `/mcp` никогда не попадают в SPA fallback.

## Границы кода

- `src/app` — router, тема и корневая композиция.
- `src/features/<feature>` — страницы, компоненты, composables и API конкретной
  предметной области.
- `@sylvieshare/share-ui` — общие для DnD Share, HavenShare и TrenchShare
  theme-токены, UI-примитивы и headless interactions. Пакет подключается одним
  публичным import API без deep imports.
- `src/shared/api` — общие HTTP-клиенты. `http.js` основан на `fetch`; любой
  non-2xx ответ является ошибкой.
- `src/shared/ui` — переиспользуемые компоненты уровня DnD Share. Компонент
  остаётся здесь, если знает о router, Pinia, HTTP API или доменной модели.
- `src/shared/composables` — поведение, не привязанное к одной фиче.
- `src/stores` — Pinia-кэши и глобальное состояние.

Новый или изменяемый Vue-компонент пишется через `<script setup>`. Правила
композиции вынесены в `md/composition-api.md`.

## Стандартные компоненты: что и когда использовать

Компоненты ниже — не локальные удобства отдельных экранов, а стандарт проекта.
Перед созданием нового оверлея, поля или drag-and-drop нужно сначала выбрать
подходящий примитив отсюда.

| Задача | Стандарт | Когда использовать |
|---|---|---|
| Низкоуровневое модальное окно | `share-ui/AppModal` | Инфраструктура backdrop, Escape, focus/слоёв, анимации и `role=dialog`. Напрямую используется только специализированными fullscreen-workspace; Escape закрывает только верхнее окно стека. |
| Стандартное окно с шапкой | `share-ui/AppModalFrame` | Единая оболочка формы, просмотра или picker поверх `AppModal`: шапка `--surface`, тело и footer `--bg`, одинаковая рамка, увеличенный заголовок и закреплённые title/крестик/мобильный handle. Тело прокручивается отдельно, footer с действиями также может быть закреплён. |
| Подтверждение | `share-ui/ConfirmDialog` | Удаление, отмена операции, сброс формы и любое решение «подтвердить/отменить». Поддерживает `loading`; не собирать собственный overlay. |
| Ввод одного текста | `share-ui/TextPromptDialog` | Создать/переименовать альбом, сцену, сущность. Заменяет `window.prompt` и локальные формы из одного input. |
| Морф-переход из элемента | `share-ui/MorphSheet` + `share-ui/useContainerMorph` | Только когда окно должно анимированно раскрываться из конкретной плитки/кнопки. На desktop фон размывается, на mobile полноэкранный sheet оставляет фон без blur. Вложенный morph задаёт `zIndex` выше родительского overlay; редакторы листа используют `3100` поверх fullscreen-листа на `3000`. Поля внутри не получают автофокус при открытии; фокус допустим после явного действия пользователя. Обычный диалог строится на `AppModalFrame`. |
| Поле формы | `share-ui/FormField` | Label, hint и горизонтальная/вертикальная раскладка одного поля. |
| Текст/число/select/многострочный текст | `FormTextInput`, `FormNumberInput`, `FormSelect`, `FormTextarea` | Любой универсальный ввод соответствующего типа. Не вводить новые локальные классы input/select без отдельной UX-причины. |
| Кнопки формы | `share-ui/FormActionButtons` | Стандартная пара отмена/сохранение и loading/disabled состояния. |
| Выбор значения | `share-ui/ValueSelect`, `SuggestPicker`, `SuggestAdd`, `SuggestMultiSelect` | Обычный select либо одиночный/множественный выбор из серверного справочника; компоненты сами отвечают за desktop dropdown и mobile sheet. `ValueSelect` открывается вниз по умолчанию, а внутри ограниченного снизу scroll-контейнера может явно использовать `drop-up`. Серверные suggest-компоненты остаются в приложении. |
| Расширенное описание | `shared/ui/InputDescription.vue` → `share-ui/RichTextEditor` | Тонкий DnD-адаптер задаёт русские подписи и owner-mode; toolbar, редактирование, очистка paste/drop и базовый HTML-контракт принадлежат пакету. |
| Отображение описания | `share-ui/RichContent` | Безопасный единообразный вывод HTML через allowlist sanitizer. Не использовать собственный `v-html` для сохранённого пользовательского контента. |
| Фильтры хроники сессии | `BasePopover` + `MultiToggle` + `FormSelect` | Локальный `SessionEventsPanel` задаёт доменные категории и чипы активного состояния; базовые popover/form controls не дублируются. |
| Плитка/карточка контента | `share-ui/BaseTile` | Общая поверхность с фоном, скруглением и тихой рамкой. Поддерживает цветовой акцент, полосу, tint, framed- и interactive-состояния; не создавать локальный базовый класс плитки. |
| Popover/контекстное меню | `share-ui/BasePopover`, `ActionMenu`, `ActionMenuItem`, `ActionMenuSubmenu` | Неблокирующий контент, привязанный к управляющему элементу. Меню поддерживает стандартный trigger и feature-trigger через slot; программно привязанный action popover выбирает `transitionPreset="action-menu"`; вложенное меню остаётся внутри visual viewport, не закрывает родителя и корректно работает на mobile. Поскольку `BasePopover` телепортируется в `body`, popover внутри модального окна обязан получить `zIndex` выше слоя своего окна; item picker прокидывает это значение через list controls. Локальный `RowActionItem.vue` сопоставляет DnD action names с Lucide-иконками, а `RowActionSeparator.vue` разделяет смысловые группы действий. Карточка-trigger использует slot-параметр `open` и общий класс `action-menu-source--open`, чтобы оставаться слегка подсвеченной всё время, пока её телепортированное меню открыто. |

| Каркас и левое меню | `share-ui/AppShell`, `share-ui/AppSidebar`, `share-ui/Sidebar*`, `share-ui/AccountMenu` | Единая геометрия приложения, DnD-стиль rail и trigger аккаунта с выпадающими действиями. Router, права, поиск, данные профиля и сами account-actions передаёт локальный adapter. |
| Каталог страницы сессии | `features/sessions/components/SessionLibraryWorkspace.vue` | Общий dotted workspace, safe-area от игроков и геометрия sidebar/detail для локаций, NPC, материалов и заданий. Предметные компоненты передают внутрь собственные список, detail и окна. |

Это не modal; вложенные точечные редакторы продолжают использовать общие dialog-компоненты. |
| Карточка выбранного объекта сессии | `features/sessions/components/SessionEntityDetail.vue` | Общая шапка, акцент, визуал, метаданные, действия, кнопка `Редактировать` и прокручиваемое содержимое для локаций, NPC, заданий и материалов. Предметные workspace-компоненты заполняют именованные слоты и не собирают собственные hero-блоки. |
| Объект сессии на холсте сценария | `features/sessions/components/SceneBlockNode.vue`, `SceneEntityBlockPreview.vue`, `SceneReferenceCreateModal.vue` | Общий заголовок каждого типа блока показывает семантическую иконку, тип и имя; материал использует иконку конкретного подвида. Picker поддерживает общий поиск, фильтр или закреплённый тип и опциональные пунктирные create-actions в заголовках групп; editor — заметки/удаление, display-list сортирует и группирует по типу. Клик открывает соответствующий холст; добавление и удаление выполняются только на самом холсте. |

Категории модальных окон:

- подтверждение — `ConfirmDialog`;
- один текстовый ответ — `TextPromptDialog`;
- сложная предметная форма — feature-компонент, но его оболочка всегда
  `share-ui/AppModalFrame`, если окну нужны заголовок и прокручиваемое содержимое;
- детальная карточка справочника — `features/handbook/components/ItemViewModal`;
  она использует `share-ui/AppModal` без отдельной полосы заголовка, поскольку
  единственной шапкой служит `ItemDetailHeader` внутри содержимого;
- серверный поиск и выбор элемента —
  `features/handbook/components/ItemPickerModal`;
- раскрытие из плитки — `MorphSheet`.

Fullscreen-карточка `AppModal` ограничивает высоту по `visualViewport`, поэтому
фиксированная шапка и поля остаются в видимой области при открытой мобильной
клавиатуре; `dvh` используется как CSS fallback.

Предметные действия не встраиваются в renderer карточки: владелец передаёт их
в footer-slot `ItemViewModal`. Поэтому одно и то же окно описания поддерживает,
например, подготовку/удаление заклинания или количество/удаление предмета, не
получая зависимостей от листа персонажа.

Все типы item используют `features/handbook/components/ItemDetailHeader.vue`.
Компонент владеет общей геометрией имени и действий, показывает панорамный
`coverImageUrl` через центрированный `object-fit: cover` и затемнение под
текстом. Для способностей (типы 3/4) и черт (тип 7), как и для профилей с
summary бестиария и заклинаний, затемняется только компактная подложка названия,
а сама обложка остаётся без общего затемнения. Справа в одной строке для любого типа справочника находятся источник
(крайний справа, полное название доступно через tooltip) и кнопка
«Редактировать» с иконкой карандаша слева от него; renderer не дублирует
источник внутри содержимого. Обложка является единственным изображением шапки:
компактная иконка в ней не дублируется и не используется как missing-cover
fallback. При отсутствии item-level обложки используется
`itemType.coverImageUrl`; все 13 встроенных типов владеют такой заглушкой.
Ошибка изображения сохраняет cover-компоновку и нейтральный фон, не переключая
геометрию карточки. Item-level обложка всегда имеет приоритет над типовой.
Типы 1/6/12 резервируют `4:3`, типы 2/8/9/11/13 — `3:2`, а типы
3/4/5/7/10 — `5:2` ещё до загрузки файла. Контейнер не ограничивается
по ширине, после загрузки использует фактическое соотношение файла и не имеет
общего ограничения максимальной высоты. `ItemDetailHeader` принимает тип
справочника и хранит расширяемую таблицу CSS-переменных минимальной высоты для
типов, которым требуется другая композиция. Обычная обложка поэтому сохраняет
своё соотношение сторон, а содержимое detail-карточки остаётся доступным через
вертикальную прокрутку. При переключении item следующая обложка сначала
декодируется в памяти, затем проявляется поверх предыдущей за `160ms`; системная
настройка `prefers-reduced-motion` отключает эффект.

Заклинание использует отдельный summary-профиль с минимальной
высотой `300px`. Уровень и школа образуют компактный вертикальный блок под
названием. Над нижней зоной справа располагается компактная обычная карточка
компонентов, а под ней время накладывания, дистанция и длительность занимают
три равные колонки. Эти краткие параметры не повторяются в содержимом ниже; для
материального компонента там остаётся только его полное описание. На узком
экране сетка остаётся трёхколоночной и уменьшает внутренние отступы и шрифт.
Для типа заклинаний назначена типовая обложка-заглушка, поэтому все заклинания
используют эту единственную summary-компоновку; персональная обложка только
заменяет изображение. Вещи типа 2 аналогично всегда держат стоимость и вес в
summary-карточках шапки, когда эти значения заданы, и не повторяют их ниже.
Плитки поверх обложек стандартизированы локальными примитивами
`features/items/components/cover`: `CoverStatCard` владеет стеклянной
поверхностью, типографикой, tone/size-вариантами и увеличенным полупрозрачным
декоративным знаком по центру справа; `CoverSummaryLayout` задаёт боковые
колонки и безопасный центр изображения; `CoverSummaryRail` с `CoverSummaryRailItem`
задаёт нижнюю сегментированную полосу и её мобильное складывание. Типовые
summary-компоненты отвечают только за выбор данных, подписей, иконок и
композиционных параметров этих примитивов.

Поиск, schema-фильтры и фильтр по публикациям принадлежат левой колонке
`HandbookItemList` и закреплены над её собственной прокручиваемой областью.
Landing справочника сразу занимает итоговую ширину до загрузки систем и
коллекций, поэтому появление данных не меняет геометрию страницы. Карточка
коллекции, мобильный type picker и вкладка модального picker используют
`itemType.iconImageUrl`; прежний `itemType.svg` не является frontend-контрактом.
`itemType.parentTypeId` связывает специализированные каталоги с родительским:
landing помечает подразделы и перечисляет их у «Вещей», а picker может рекурсивно
включить дочерние типы без хардкода их идентификаторов.
`ItemIcon` применяет эту растровую эмблему только после отсутствующих item-level
`iconImageUrl` и `svg` в списках, picker и глобальном поиске. Detail-шапка
всегда использует независимый cover-контракт. Полоса
группировки списка отделена левой и нижней границами без правой рамки.
Широкая collection bar страницы содержит только возврат, название, счётчик и
добавление объекта. Тот же list-owned паттерн используется в picker-модалках,
поэтому фильтры не меняют положение между справочником и сценариями выбора.
`ItemPickerModal.fixedFilters` задаёт обязательные условия предметного выбора:
они сразу участвуют в серверном запросе, видны в общей панели фильтров и
заблокированы для изменения или сброса пользователем.

Бестиарий использует отдельный профиль с нижней границей `440px`. Фактическое
соотношение обложки задаёт предпочтительную геометрию, но портретный файл
ограничивается квадратным окном 1:1: изображение само по себе никогда не делает
шапку выше своей ширины. Production-файл `1536×1152` по-прежнему раскрывает
шапку до 4:3, а более объёмная сводка при необходимости может увеличить её
высоту, чтобы характеристики не обрезались. При смене существа профиль
сразу резервирует 4:3, не меняя соотношение на время загрузки, поэтому
переход между подготовленными обложками не меняет высоту. Формат рассчитан на высокую
композицию и боковое кадрирование на мобильном. У такой шапки нет общего
затемнения изображения: название получает компактную тёмную подложку по
содержимому, а источник, теги, основные боевые параметры, скорости и все шесть
модификаторов характеристик выводятся через summary-slot в собственных
полупрозрачных блоках. На desktop CSS Grid оставляет центральную область
обложки свободной: CR и КД стоят слева, хиты, мастерство и скорости — справа,
мировоззрение остаётся справа над сводкой, а остальные теги
стоят слева между именем и CR. Шесть характеристик образуют нижнюю полосу.
Сводка занимает всю свободную
высоту шапки, поэтому при коротких боковых группах полоса характеристик всегда
прижата к нижнему краю. На экранах до `520px` боковые группы переходят в две
колонки, характеристики — в сетку `3×2`. Навыки и
последующие разделы начинаются уже под изображением. Если содержимое сводки не
помещается на узком экране, шапка растёт по высоте, а не обрезает данные.
Оставшееся содержимое detail-карточки прокручивается по вертикали, в том числе
внутри модального окна и на узких экранах.
Типовые detail renderer получают `showTitle=false` и отвечают только за
содержимое ниже общей шапки. Технический ID объекта не занимает место на
обложке: `HandbookItemDetail` выводит его приглушённой строкой в самом низу
detail-содержимого.

Полноценные смысловые блоки специализированных detail renderer оформляются
через общий `shared/ui/DetailSection`: тематическая иконка, контрастный
uppercase-заголовок и затухающая линия связывают оружие, предметы, способности,
заклинания, существ, черты и доспехи в одну визуальную систему. Боевые блоки
используют `tone="combat"`, а повторяемые карточки с собственным названием и
описанием — `shared/ui/DetailEntryCard`. Специализированные hero/stat-блоки
типов сохраняют собственную композицию.

`window.alert`, `window.confirm`, `window.prompt` и вручную собранные во feature-коде
`position: fixed` backdrop-оверлеи запрещены. Shared picker/reporting primitives
могут владеть специализированным sheet/highlight слоем. Ошибка поля показывается рядом с
полем; ошибка операции — в состоянии формы/экрана. Если требуется новая
повторяемая категория диалога, сначала добавляется обобщённый компонент в
`shared/ui`, затем он используется фичами.

## Навигация приложения

На desktop локальный `shared/ui/DesktopSidebar.vue` является adapter-ом над
`share-ui/AppSidebar` и nav-примитивами. В свёрнутом состоянии rail занимает 64 px,
показывает иконки разделов и оставляет эту полосу в layout страницы.
Раскрытый rail имеет ширину 224 px и показывает подписи, поиск и профиль;
рабочая область синхронно меняет левый отступ с 64 до 224 px, поэтому rail не
перекрывает контент и его визуальная ширина совпадает с зарезервированной в layout.
Групповые маркеры имеют одинаковую высоту в обоих состояниях: раскрытый rail
показывает название категории, а свёрнутый — горизонтальную линию на его месте,
так что позиции следующих иконок не меняются из-за скрытия заголовка. При первом
открытии rail раскрыт; после первого ручного переключения его состояние
сохраняется в local storage внутри общего компонента. Локальный
adapter владеет router,
авторизацией, поиском, account-actions и иконками. Список доступных разделов общий
с мобильным меню и задаётся `shared/lib/appNavigation.js`. «Справочник» остаётся
самостоятельным публичным пунктом без группового заголовка, а публичный пункт
**«Правила игрока»** входит в группу **«Для игрока»**. Гость видит в этой группе
**«Создать персонажа»**. Авторизованный пользователь без персонажей видит тот же
пункт, а после появления первого персонажа он заменяется на **«Персонажи»**. Над поиском расположен
`shared/ui/GameContextSelector`: в раскрытом
rail он одной компактной строкой показывает текущую систему и менее акцентную
редакцию, а в свёрнутом rail и мобильной шапке использует кнопку-иконку. В обоих
случаях подробные listbox системы и редакции появляются только в popover по
нажатию. Авторизованный выбор
сохраняется через account API в БД, гостевой — в local storage. Иконка
списка-документа обозначает сессии, а иконка группы людей —
персонажей. Поиск является первым элементом навигации сразу
под игровым контекстом: клик по его иконке в свёрнутом rail раскрывает панель и сразу
переводит фокус в поле с placeholder **«Поиск по справочнику»**, а список найденных вариантов раскрывается справа
от панели без изменения layout страницы. Popover появляется и скрывается плавно;
при уточнении запроса строки и секции анимируют добавление, удаление и смену
позиции. Результаты группируются по конкретному типу предмета или словарной
подсказки; локальные материалы D&D 5e 2014 образуют отдельную группу «Правила»
и ведут прямо к статье. Они появляются до завершения серверного запроса и
остаются доступны при ошибке API справочника. Область поиска ограничена текущей
системой и редакцией; локальные статьи правил подключаются только для D&D 5e
2014. Ссылка «Правила» вычисляется из того же контекста. Служебное действие
**«На странице ошибка»** находится в нижнем блоке
прямо над кнопкой раскрытия/сворачивания rail; в мобильной шапке оно находится в
меню бренда. Для гостя account-блок в раскрытом rail показывает действия
**«Войти»** и **«Регистрация»**, а в свёрнутом — стандартную иконку входа с
доступным названием и браузерной подсказкой **«Войти»**.

На ширине до 640 px desktop rail скрыт, а сверху используется
`AppHeader`.

Бренд **DnD Share** в desktop rail, мобильной шапке и favicon использует один
растровый портрет сереброволосой эльфийки из
`frontend/public/brand-mascot.webp`: угловатый почти чёрный капюшон, длинные
серебряные пряди, светлые серо-зелёные глаза, заострённое ухо и глубокий
сливовый контур. Это тот же персонаж, который появляется на сюжетных обложках
справочника, а не отдельный бренд-маскот. `favicon-32.png`, `favicon.ico` и
`apple-touch-icon.png` являются уменьшенными производными мастер-портрета и не
редактируются как самостоятельные варианты. SVG-аппроксимация не используется:
она слишком сильно упрощает лицо и характер персонажа.

### Маскот DnD Share

Канонический образ, неизменяемые признаки, библиотека поз и правила для
сюжетных обложек описаны в [`md/mascot.md`](./mascot.md). Компактный
`brand-mascot.webp` остаётся самостоятельной композицией головы и плеч, но не
самостоятельным персонажем: он сохраняет лицо, волосы, ухо, капюшон и палитру
полноразмерного маскота. Мастер хранится с настоящим прозрачным alpha-каналом и
проверяется на светлом и тёмном фоне в размерах 64, 32 и 16 px; в favicon не
добавляют оружие, магию, текст, мелкие ремни, рамку или фоновую сцену.

Действие **«Аккаунт»** находится в меню профиля непосредственно над выходом и
ведёт на `/account`. Страница имеет две доступные keyboard-вкладки: смена пароля
и использование пространства. Вторая вкладка загружает статистику только при
первом открытии, показывает общую `SegmentDonutChart`, счётчики неизвестных
размеров и подробный список личных изображений, SVG, видео и музыки. HTTP и
авторизация остаются в feature-коде; в `share-ui` вынесена только механика
нейтрального графика.

По умолчанию маршрут использует режим `flow`: `AppHeader` находится в обычном
потоке документа и естественно уезжает вместе со страницей без JS-наблюдения за
`window.scrollY`. Полноэкранный workspace с собственным scroll-контейнером может
явно задать `meta.mobileHeader: 'collapsible'`. Такой экран регистрирует активный
DOM `Element` через `shared/composables/useAppHeaderCollapse.js`; контроллер один
владеет scroll/touch listeners и состоянием `ui.headerHidden`. Полноэкранный
экран со своей навигацией может использовать `meta.mobileHeader: 'hidden'`:
тогда `AppHeader` не отображается на ширине до 640 px, а контент занимает всю
высоту viewport.

Feature-компоненты не должны самостоятельно слушать `window` или записывать
`headerHidden`. При смене вложенной вкладки workspace перерегистрирует её scroll
element. Для измерения внутренних toolbar передаётся явный DOM-ref; `$el`
Vue-компонента не является допустимым контрактом, потому что fragment-компонент
может вернуть text/comment anchor вместо `Element`.

Мобильная шапка всегда сохраняет бренд **DnD Share** и его выпадающую навигацию,
но не дублирует title текущей страницы. Кнопка **Назад** показывается только у
вложенного состояния и ведёт к явно заданному родителю, а не по истории browser:
например, сессия → список сессий, создание персонажа → список персонажей. У
корневых списков кнопки нет. В справочнике сначала снимается вложенный `item`,
затем `type`, и только после этого используется родитель маршрута.

Страница может уточнить компактный chip через
`ui.setHeaderContext({ chip }, route.name)`: так экран сессии показывает её
статус. Контекст привязан к имени маршрута, поэтому
данные предыдущего экрана не используются как fallback; при размонтировании
владелец вызывает `clearHeaderContext(route.name)`. Title страницы остаётся в
`route.meta` для router и transition semantics, но в мобильной шапке не
выводится. Режим `mobileHeader: 'hidden'` имеет приоритет над содержимым header.

## Drag-and-drop

`useSortable` из `@sylvieshare/share-ui` — единая механика списков сцен, музыки, инвентаря и других
сортируемых коллекций. Feature-компонент отвечает только за идентификатор
группы, отображение placeholder и сохранение результата. Расчёт индексов,
pointer lifecycle и перенос массива не копируются в компонент.

Для простой перестановки после drop используется `reorderByDrop(items,
fromIndex, toIndex)`. Для нескольких контейнеров используются группы
`useSortable`; DOM-контейнер помечается `data-sortable-container`. Элемент с
`data-sortable-key` может находиться внутри нейтральной UI-обёртки, например
`RowActionMenu`: индекс считается по ближайшему sortable-контейнеру, поэтому
вложенные сортируемые списки не смешиваются с родительским.

Свободная раскладка кампании использует отдельную pointer-модель, а не сортировку
списка. `SessionGraphCanvas.vue` держит один постоянный экземпляр
`NestedGraphCanvas.vue`, который владеет pan, zoom, перетаскиванием узлов и hit
targets связей. При переходе глава → сценарии → блоки меняются только nodes,
edges, размеры карточек и ключ сохраняемого viewport; второй физический холст не
монтируется. `useChapterGraph.js`, `useSceneGraph.js` и
`useSceneBlockGraph.js` раздельно владеют серверным состоянием уровней и
optimistic preview координат. В local storage сохраняется только viewport,
позиции и связи остаются серверным состоянием.
После преодоления порога drag-жеста `NestedGraphCanvas` один раз эмитит
`drag-start`; владелец уровня закрывает открытые action-menu до начала preview
координат. Pointer-down без фактического перемещения остаётся обычным кликом.

Отдельный workspace state страницы сессии сохраняет режим, уровень вложенности,
главу и выбранный сценарий. Он восстанавливает холст сценария/элементов после
перезагрузки и служит return-context: закрытие боя возвращает пользователя на
тот уровень, откуда бой был открыт. Его переходы представлены одной фазой
`idle/opening/open/closing`; уровень холста и выбранный id сценария вынесены в
`useSessionGraphNavigation`, поэтому компоненты не держат параллельные копии
объекта сценария. Optimistic drag-preview ограничен одним обновлением на кадр,
а запись viewport в local storage выполняется с debounce.

На всех трёх уровнях завершение link-жеста сразу создаёт переход без
промежуточного окна. Клик по линии или уже показанной подписи открывает
`BasePopover` с отдельными действиями изменения необязательной подписи (до 240
символов) и удаления перехода; create/update/delete сразу синхронизируют
соответствующий edge в серверном graph state через `POST`, `PATCH` и `DELETE`
routes. Во время link-жеста наконечник временной стрелки совпадает с курсором,
а линия автоматически выходит из центра ближайшей к нему стороны карточки.
Активное создание связи отменяется через `Esc` или ПКМ; браузерное контекстное
меню подавляется только пока выбран исходный узел.
Готовые переходы также выбирают обращённые друг к другу центры левой, правой,
верхней или нижней стороны. Меню связи на каждом уровне позволяет менять
подпись, переключать одно-/двустороннее направление и разворачивать
одностороннюю связь; для двусторонней связи лишнее действие разворота скрыто.
Первая и последняя части существующей кривой имеют широкую невидимую hit-area:
hover подсвечивает конкретную связь, а drag этой области к другой карточке
переставляет соответствующий конец через тот же PATCH. Поэтому сходящиеся в
один порт линии остаются доступны до общей точки. При создании и перестановке
наведение на допустимую карточку заменяет линию к курсору полноценным preview
будущего соединения между портами; наконечники сохраняют выбранную
направленность.

На третьем уровне `NestedGraphCanvas` читает индивидуальную ширину блока и
измеряет фактическую DOM-высоту через `ResizeObserver`, поэтому границы связей
следуют за содержимым. Drag правой границы даёт optimistic preview ширины и
сохраняет её через `useSceneBlockGraph`; эта механика не включается для глав и
сценариев с фиксированным размером.

Выбор фоновых изображений глав, сценариев и локаций использует общий
`SessionImagePicker`: в форме он показывает только текущую картинку и действие
смены. Отдельное окно выбора содержит единый прокручиваемый каталог с секциями
и верхними якорями категорий, а не вкладки с разрозненными списками. Тот же
компонент принимает отдельный NPC-каталог. Оба каталога загружаются API и
кэшируются на клиенте; карточки получают готовый `imageUrl`, поэтому локальных
preset-путей и второго контракта для загруженных файлов нет.

Контекстные действия создания выводятся через `CanvasActionDock.vue` поверх
холста сверху справа, перед открытыми окнами правой панели инструментов; когда
все окна закрыты, dock прижимается к правому краю холста. Каждый action —
отдельная стеклянная кнопка без общего tile-контейнера. Командная шапка сессии
является обычным `header` с собственным фоном и нижним разделителем, а не
`BaseTile`: в ней находятся
session/arc/combat controls и переключатели панелей кубиков, музыки и лога. Формы и
разрушающие действия графа используют `AppModalFrame` и `ConfirmDialog`, обычный
клик по узлу/связи — `BasePopover`.

Контекст входа в бой берётся у постоянного `SessionGraphCanvas`: на уровне
элементов он содержит закреплённые главу и сценарий, передаётся как одним
действием блока «В бой», так и combat-кнопкой командной шапки, а затем хранится
в workspace state. Боевая панель освобождает слева место под одну или две
контекстные карточки, не создавая отдельный breadcrumb или второй холст. Её
desktop-правая граница не зависит от видимости правых tool-панелей.

## Форматированные описания

Пара `share-ui/RichTextEditor` + `share-ui/RichContent` является единым
контрактом расширенного описания. Локальный `InputDescription` только адаптирует
этот контракт к DnD-состоянию. В данных хранится очищенная HTML-строка текущего
формата; allowlist sanitizer применяется при paste/drop, выдаче из редактора и
перед read-only DOM render. Обычные ссылки редактирует сам `RichTextEditor`.
Предметные inline-узлы хранятся атомарным
`span[data-rich-node][data-rich-payload]`: `share-ui` владеет безопасным
HTML-контрактом и selection API, а `DndRichContent` — значениями `dice`, `item`
и `suggest`, их загрузкой и действиями. `suggest` в расширенном тексте означает
конкретный термин малого справочника (например навык или состояние), а не ссылку
на раздел каталога; при активации он показывает описание термина. `InputDescription` добавляет кнопки этих
трёх типов через toolbar slot: на широкой панели это семантические Lucide-иконки,
рядом с которыми находится нативное действие обычной ссылки; при недостатке
ширины все четыре действия сворачиваются в одну кнопку с подписанным меню.
Область редактирования прозрачная и отделяется от окружающей формы рамкой; клик
по существующему chip открывает действия изменения и удаления. Не добавлять параллельные поля
`desc/description` ради совместимости: у каждой сущности в схеме должен быть
один документированный ключ.

В read-only тексте предметные inline-узлы не имитируют отдельные bordered-chip:
ссылки на `item`/`suggest` используют низкую полупрозрачную подложку и
приглушённый знак, а `dice` — более компактную цветную подложку без рамки и с
увеличенным боковым внешним отступом. Цвет усиливается только при наведении или
keyboard focus, поэтому узлы остаются заметными действиями, но не дробят прозу.

Read-only `DndRichContent` и текстовая область `InputDescription` используют
отдельный книжный шрифт `--font-prose` (Literata в DnD Share). UI-кнопки,
метаданные и короткие подписи остаются в `--font-ui`, а заголовки сущностей — в
`--font-display`. Та же prose-роль применяется к статьям правил, полноценным
описаниям мира и текстовым материалам сессии; короткие карточные excerpts,
ошибки и служебные сообщения не считаются long-form только из-за имени поля
`description`. Технические ключи, формулы, идентификаторы и логи используют
единый `--font-mono`.

`dice` хранит `{formula,label?,average?}` и показывает ручное среднее перед
составом формулы через `SystemDie`; клик отправляет выражение в общий dice store.
Формулы поддерживают сложение, вычитание и умножение, включая редкие
импортированные выражения вида `1к6 × 5`. DnD-адаптер принимает необязательное
имя субъекта: в карточке существа оно передаётся в бросок отдельно от действия и
попадает в `actorName` журнала. Карточка, открытая из encounter, проводит этот
контекст через `ItemViewModal` и добавляет к имени букву экземпляра. `item` хранит `{id,typeId}`,
показывает короткий hover-preview и открывает `ItemViewModal` по клику. `suggest`
хранит `{id,typeId}` и раскрывает описание в `BasePopover`. Legacy custom tags
не являются runtime-контрактом; рекурсивная startup migration переводит их во
всех HTML-строках item data в `dice`, `item`, `suggest` либо безопасную нативную
ссылку и идемпотентно пропускает уже актуальные узлы.

## Персонажи и игровые системы

`features/character-editor/settings/index.js` — реестр поддерживаемых систем.
Для каждой системы он задаёт:

- schema/layout листа из кода;
- semantic accessors для имени, аватара, подзаголовка, уровня, HP, AC и
  инициативы;
- создание начального payload, если оно отличается от D&D wizard.

`char_template` хранит только `id` и `name`. Полей `schema`, `createForm` и
`pathValues` нет. Список персонажей, toolbar и сессии используют одни и те же
accessors; чтение путей из БД не допускается. D&D и VTM зарегистрированы в коде.

Канонические D&D-данные читаются только в текущем формате: `lvl` — объект,
`classes` — массив, характеристики имеют `value {base,bonuses}`, `speed` —
`{base,bonuses}`, `hp.hitDice` — массив, `spells` — объект, инвентарь —
`{equipped,sections}`, деньги — `{order,amounts}`. Преобразование старых данных
выполняет startup-схема из `internal/store/schema/*.sql` до начала
HTTP-обслуживания; компоненты не содержат read-time миграций.

Фиксированный каталог кубиков находится в `shared/lib/systemDice.js`, а все
экранные многогранники и выпавшие значения рисует `shared/ui/SystemDie.vue`.
Кубики не зависят от Pinia suggest store.

## Router

Актуальные страницы: `/`, `/sessions`, `/sessions/:uuid`, `/screen/:uuid`, `/join/:code`,
`/chars`, `/chars/new`, `/char/:uuid`, `/char/:uuid/print`, `/handbook`,
`/handbook/dictionary`, `/handbook/objects`, `/rules`, `/rules/:articleSlug`,
`/admin`. Неизвестный клиентский
маршрут перенаправляется на `/`.

Вкладка `/admin` «Статистика» показывает не только счётчики сущностей, но и
общий объём управляемого файлового хранилища. Общий `SegmentDonutChart` строит
разбивку системных и пользовательских изображений, видео, системной и
пользовательской музыки и SVG; рядом выводятся число объектов и предупреждение
о файлах с неизвестным размером. На узких экранах график и сводка переходят в
одну колонку.

В `/admin?tab=ui-kit` через отдельный `@sylvieshare/share-ui/gallery`
подключается `ComponentGallery`. Это единая интерактивная витрина библиотеки:
она использует DnD-тему и accent приложения. На уровне исходников компонент
запрашивается через `defineAsyncComponent`; production-конфигурация dndShare
намеренно сводит весь JavaScript в один стабильный файл, чтобы открытая вкладка
не получала 404 после deploy, поэтому отдельного runtime chunk здесь нет. Новый
публичный визуальный компонент `share-ui` обязан появиться на этой доске —
полноту проверяет тест самой библиотеки.

`/screen/:uuid` uses `meta.standaloneView`: like print mode, it removes the
global sidebar, header and diagnostic overlays, but retains the dark application
theme for a public read-only encounter display.

Router prefetch хранится 30 секунд и используется страницами списков. Направление
перехода определяется `meta.section/depth/pageOrder`; навигационные компоненты
не должны вычислять его повторно. На desktop страницы сменяются последовательно.
На ширине до 768 px приложение использует root View Transition: переход вперёд
мягко вводит новый экран справа, а возврат сдвигает верхний экран вправо и
открывает готовый родительский. В единый snapshot входят и страница, и `AppHeader`,
поэтому граница полноэкранного листа персонажа не вызывает отдельной перестройки
шапки. Длительность мобильного перехода — 380 мс. Для браузеров без View
Transition входящая и исходящая страницы перекрываются CSS-анимацией, а исходящая
страница исключается из потока. При `prefers-reduced-motion: reduce` анимация
отключается. View Transition update callback ждёт завершения роутинга через
`afterEach` и следующий Vue `nextTick`; ожидание `requestAnimationFrame` внутри
callback запрещено, поскольку браузер может приостановить кадры до завершения
DOM update и прервать переход по timeout. Все служебные promises View Transition
наблюдаются, поэтому штатная отмена анимации не создаёт глобальную ошибку.

## CSS

Общая палитра и canvas приходят из `@sylvieshare/share-ui/styles.css`, который
импортируется один раз в `main.js`. `src/app/theme.css` задаёт DnD-акцент,
layout, доменные цвета и продуктовые prose/mono/print font stacks. Cormorant
Garamond и Literata подключаются как variable web fonts; display-роль не
запрашивает веса выше поддерживаемого `700`. `npm run check:colors` входит в production build и
запрещает новые прямые hex/RGB/HSL значения. Подробности — `md/css-variables.md`.

## Обновление share-ui

### Cross-repository сопровождение

Задача в DnD Share является разрешением без дополнительного согласования
изменить соседний `../share-ui`, когда существующий общий API содержит баг или
не позволяет корректно завершить задачу. В рамках задачи разрешены изменения
исходников, тестов, галереи и документации библиотеки, release commit/tag/push,
а затем обновление точной версии и lock-файла DnD Share.

Изменение обязано оставаться нейтральным: `share-ui` не получает router, Pinia,
HTTP API, permissions, локализованные DnD-тексты и доменные модели. Такая логика
остаётся в локальном adapter/controller. Нехватку общего API не обходят копией
компонента, deep import, правкой `node_modules` или постоянным переопределением
его базовой геометрии. Если безопасное решение требует незапланированной
breaking-миграции других продуктов, перед выпуском нужно завершить их миграцию
либо запросить решение пользователя.

Канонический порядок работы, матрица проверок, versioning и Definition of Done
описаны в
[share-ui/MAINTAINING.md](https://github.com/SylvieShare/share-ui/blob/main/MAINTAINING.md).

DnD Share использует точный HTTPS-архив release tag; floating branch и локальная
`file:` dependency не допускаются. Обновление выполняется после выпуска новой
версии в `SylvieShare/share-ui`:

```bash
cd frontend
npm install --save-exact \
  "https://github.com/SylvieShare/share-ui/archive/refs/tags/vX.Y.Z.tar.gz"
npm test -- --run
npm run build
```

Изменения межпроектного примитива сначала делаются и документируются в
`share-ui`, затем consumer обновляет tag. Файлы внутри `node_modules` не меняют.

## Политика изменений контракта

Runtime поддерживает только текущий контракт. Если изменение ломает старый
формат, нужно:

1. добавить идемпотентное исправление данных в подходящий
   `internal/store/schema/*.sql`;
2. переключить все producer/consumer на новый формат;
3. удалить старые поля, ветки чтения, aliases и временные admin jobs;
4. обновить `md/` и тесты.

Сохранение двух форматов «на всякий случай» не допускается.
