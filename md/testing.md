# Проверки проекта

Единая точка входа из корня — `python3 scripts/test.py all`. Результат содержит
статус и время каждого набора; ошибка одного набора не скрывает остальные.
Команда не читает `.env` и не обращается к production-БД.

| Профиль | Что выполняет |
| --- | --- |
| `fast` (по умолчанию) | Go unit, vet/build, Vitest и frontend build, Node-тесты инструментов, Python-тесты deploy/справочника/миниатюр, проверка wiki. |
| `db` | Все Go-тесты с обязательным PostgreSQL, затем vet/build. |
| `browser` | Браузерные UI/карты/production-проверки и отдельный frontend → Go → PostgreSQL smoke авторизации. |
| `models` | Python/Blender-проверки геометрии и браузерная диагностика локальных моделей/GPU. |
| `all` | Все перечисленные наборы, Go запускается сразу с БД. |

Нужны установленные зависимости frontend, Chromium Playwright, Go и PostgreSQL
(`initdb`, `pg_ctl`, `createdb`). `models` также требует Blender и Python с NumPy.
На macOS используются Blender.app и его Python; на других системах можно задать
`BLENDER_BIN` и `MODEL_PYTHON`. Node-инструменты моделей используют окружение,
подготовленное `scripts/maps/setup-model-tools.sh`.

## Изоляция PostgreSQL

Профиль `db` автоматически создаёт временный локальный кластер с UTF-8 и свободным
портом, запускает проверки и останавливает/удаляет кластер даже после ошибки.
Для внешнего тестового кластера можно задать `DNDSHARE_TEST_DSN` — postgres URL
с host `127.0.0.1` и родительской БД `dndshare_test_*`. Пользователю нужна
возможность создавать БД. Эта родительская БД не очищается: `internal/testdb`
создаёт отдельную случайно названную БД для каждого теста и удаляет только её.
Go-пакеты могут выполняться параллельно.

`DNDSHARE_TEST_REQUIRED=1` превращает отсутствие DSN в ошибку. Runner включает
этот флаг для DB-профиля, поэтому успешный DB-прогон означает выполненные
интеграционные проверки. Обычный `go test ./...` без DSN явно пропускает их.
Новые HTTP-тесты авторизации и browser smoke используют полную текущую схему из
реальных миграций. Фикстуры feature-тестов содержат только собственные данные;
исторические преобразования данных для их подготовки не запускаются. Изолированные
SQL-проверки отдельных store-методов могут использовать текущий DDL предметных
таблиц и минимальные stubs для несвязанных таблиц; эти фикстуры не подменяют
проверки настоящего HTTP API с полной схемой.

Сценарии истории, применений, переводов, инвентаря и хроники получают отдельную
фикстуру/БД. Они запускаются независимо через поднаборы
`TestCharacterSessionPersistencePostgres`; порядок сценариев не создаёт тестовые данные.

## Браузерные наборы

Общая конфигурация — `frontend/playwright.suite.config.js`; `playwright.config.js`
и прежние feature-конфиги — короткие совместимые обёртки без собственных серверов и настроек:


- `ui`: браузерные компонентные/функциональные сценарии на Vite;
- `maps`: обычные сценарии карт на Vite, один worker для WebGL;
- `production`: мировые карты и загрузки изображений на production build;
- `models`: отдельный диагностический запуск с `DNDSHARE_TEST_MODELS=1`;
- `fullstack`: собранный frontend и настоящий Go API на изолированном PostgreSQL;
  его сервер и URL создаёт Go-тест из профиля `browser`.

Обычные сценарии не зависят от содержимого игнорируемого `models/`. Проверки
с тегом `@local-model` требуют подготовленных файлов, `@gpu` — браузерного GPU
таймера. В диагностическом профиле недоступные ресурсы явно отмечаются как skip;
замеры SwiftShader не считаются измерением аппаратного GPU.

Примеры узких запусков из `frontend`:

```bash
npm test
npm run test:browser -- --project=maps tests/maps/resilience.spec.js
npm run test:browser -- --project=production tests/global-maps
npm run test:models
```

Runner выбирает свободные порты; ручной браузерный запуск использует 15440/15441.
Серверы запускаются с `strictPort` и без переиспользования постороннего сервера.
У каждого тестового Vite-сервера собственный cacheDir в target/vite-cache,
поэтому параллельные порты и checkout не перезаписывают кеш активного dev-сервера.
`forbidOnly` включён для всех проектов. При ручном запуске JSON сохраняется в каталоге test-results frontend под именем
results.json. Runner сохраняет раздельные отчёты browser/models/fullstack в
каталоге target/test-reports frontend. Пути можно задать через
`DNDSHARE_BROWSER_REPORT` и `DNDSHARE_BROWSER_OUTPUT`.

## Контракты и качество фикстур

Сетевые подмены должны сопоставлять `url.pathname.startsWith('/api/')`, а не
`**/api/**`: широкая маска перехватывает также JS-модули `/src/shared/api/`.
Фикстуры записей реализуют текущий протокол `baseVersion`, `mutationId`, `patches`
и чтение `/changes`; неизвестный формат нельзя заменять старым `version/data`.

SSE-конверты Go и JS сверяются с
`internal/web/testdata/session-live.json`; общий контракт патчей —
`internal/documentpatch/testdata/contract.json`. Уведомления получают данные
`chronicle`, а не прежнюю инвалидацию `journal: true`.

UI-тест проверяет действие и результат: сохранение, запрос, доступность контрола,
смену состояния, сохранность черновика после ошибки. Проверки исходных строк,
имён переменных и точного CSS не заменяют такое поведение. Общий контракт
композиции проверяется у общего компонента, правила предметной области — отдельно
у потребителей. Статические проверки допустимы для архитектурных ограничений,
например DDL-only миграций. Для неизменяемого формата пароля используется
фиксированный независимо вычисленный PBKDF2/SHA1 вектор, а не второй round-trip.
Для SSR-композиции доступен `frontend/tests/unit/renderComponent.js`: он создаёт
отдельное приложение для каждого рендера, принимает slots, plugins и provide.
Pinia и предметные фикстуры создаются внутри теста, без общего состояния между сценариями.
