# Проверки проекта

Полный набор выполняется **только по прямой команде пользователя**:
`python3 scripts/test.py all --full` или `python3 scripts/ui.py verify --full`.
Обычная разработка и выпуск не являются разрешением на полный прогон. `npm test` и frontend
build также выполняют `check:bindings`: необъявленные переменные JS/Vue являются
ошибкой проверки. Результат содержит
статус и время каждого набора; ошибка одного набора не скрывает остальные.
Команда не читает `.env` и не обращается к production-БД.


## Матрица проверок

### Игровые механики листа

`python scripts/test.py mechanics` запускает профиль веба и Android. Для одного клиента
используйте `python scripts/mechanics/run.py --client web` или `--client android`.
Профиль входит в `test.py all --full`. Для веба нужны установленные зависимости
из `frontend` и Chromium Playwright либо путь в `DNDSHARE_BROWSER_EXECUTABLE`.
Для Android нужны JDK и Android SDK. Эмулятор для этих расчётов не требуется.

Оба клиента открывают одни и те же сценарии из `native/fixtures/game-mechanics/`.
В каждом заданы каталог, документ персонажа, действие и ожидаемый результат.
Веб проверяет и путь автора через интерфейс: создать правило, ограничить область
броска, сохранить, открыть заново и увидеть результат на листе. Наборы для
ресурсов, выбора, оружия, заклинаний, состояний и действий перечислены в
`scripts/mechanics/suites.json`. Новый тип результата требует общего сценария.
У нового блока редактора должны быть указаны проверки обоих клиентов.

При заданном `DNDSHARE_TEST_DSN` профиль запускает также
`TestAuthoredEffectBindingsPostgres` и `TestStatusSaveLostResponsePostgres`.
Первый тест сохраняет новые эффекты и заклинания через обычные HTTP API,
читает их заново, применяет заклинания на разных кругах и проверяет параметры
состояния и расход ячейки. Общие случаи находятся в
`native/fixtures/game-mechanics/effect-bindings.json`. Веб и Android проверяют
бонус к атаке и число костей по тем же случаям, включая выбор конкретного оружия.
Браузерные тесты проходят создание связи с нуля и повторное сохранение через
штатный редактор.

В проверке потери ответа клиент входит через HTTP, прокси обрывает
соединение после фиксации броска, затем клиент повторяет тот же POST. Проверяются
квитанция, число событий, версия документа и состояния персонажа. Для запуска
только этого случая укажите `DNDSHARE_TEST_REQUIRED=1` и выполните
`go test -count=1 ./internal/web -run '^TestStatusSaveLostResponsePostgres$'`
с [изолированной базой](#изоляция-postgresql).

Отдельно запустите `python scripts/mechanics/catalogue_audit.py --live --report build/mechanics-audit.json`
для сверки с опубликованным справочником. Аудит читает схемы и словари вместе
с записями, разрешает скрытые цели по ID, проверяет ссылки на предметы, источники
ресурсов, варианты выбора и параметры эффектов. В отчёте указаны ID предмета,
путь поля и причина. Код выхода 1 означает, что есть замечания, включая поля
вне текущей схемы. Чтобы сохранить исходные данные для воспроизведения,
добавьте `--save-snapshot build/catalogue-input.json`. Для проверки без сети
передайте этот файл через `--snapshot`.

Набор определяется изменённым поведением. Если задача затрагивает несколько
строк, выбираются их относящиеся к изменению проверки; это не запускает
автоматически все тесты проекта. Неограниченные web-unit и общие
browser/fast/all профили требуют прямой команды пользователя. Для Android
выбираются затронутый модуль и instrumentation-классы. Строгая проверка wiki
(`python3 scripts/check-wiki.py --strict`) нужна при правке документации.

| Изменение | Обязательный набор | Дополнительные условия |
| --- | --- | --- |
| Только Markdown | `python3 scripts/check-wiki.py --strict`, чистый diff и проверка перенесённого текста | Runtime build и deploy не нужны; не менять продуктовые контракты под видом переноса. |
| Инструменты документации | Проверка wiki и `python3 -m unittest discover -s scripts/docs -p 'test_*.py'` | Тестировать ссылки, якоря, предупреждения и исключения для отчётов; для Node-инструмента выполнить его `node --test` сценарии. |
| Косметика (цвет, текст, иконка, локальный отступ) | Сборка затронутого клиента и одна визуальная проверка | Без обязательных lint Android, инструментального теста, трёх форматов, парного отчёта и PostgreSQL. Если меняются переносы или переполнение, применить строку раскладки. |
| Действие, жест, анимация или раскладка | Одна проверка изменённого поведения и сборка. Для общего UI сверить оба клиента | Три формата нужны при изменении адаптивной раскладки, её порогов или переходов между форматами. Отдельный отчёт по мелкой правке не требуется. |
| Инструменты разработки и выпуска | Узкие тесты изменённых инструментов и пробный прогон затронутого пути | Выпуск проверяется на изолированном стенде. Сайт ради правки инструментов не перезапускают. |

| Логика Android, хранилище или жизненный цикл | Узкий unit-тест логики или `DeviceTest` с нужным классом и сборка APK. HybridShellTest для оболочки; browser offline-сценарии для данных и sync | Lint нужен для изменений платформенных API, разрешений и ресурсов. | SQL, Store, права/атомарность API или формат документа | `python3 scripts/test.py db`, затронутые frontend-тесты при изменении DTO | Только изолированный PostgreSQL; фикстуры текущей схемы и настоящий HTTP-контракт. |

| Перед выпуском runtime | Проверки затронутых строк и одна production-сборка. Go test/vet при изменении Go-кода | Проверяют и передают один артефакт из чистого commit. После выкладки сверяют readiness. Порядок описан в [deploy](deploy.md). |

Браузерный прогон читает стабильные исходники. Не менять их во время тестов:
Vite HMR может перезагрузить страницу и исказить результат. Для параллельной
работы запускать тесты из отдельной копии проверяемого состояния.

## Профили runner

Нативные Gradle-проверки запускаются отдельно на Windows из
[инструкции сборки](../native/README.md). `testDebugUnitTest` проверяет чистую
логику, а `connectedDebugAndroidTest` — Room/SQLite и Ktor MockEngine на Android:
прерванный bootstrap,
возобновление с сохранённого cursor, офлайн-поиск/описание, изоляция систем,
tombstones, visibility manifest, reset, пустой delta, фильтры/счётчик до LIMIT и отмену проверки сессии
при выходе. Server DB tests проверяют
pagination, права, сохранность строки после soft delete и порядок committed ревизий.

Общий UI и игровой код проверяются браузерными сценариями. Android-оболочка
проверяется HybridShellTest на выделенном эмуляторе: упакованный интерфейс,
SQLite после пересоздания Activity и WebGL2. Прежний Compose/API smoke удалён.
Автономные данные, восстановление очереди и выход проверяет tests/offline/platform.spec.js.


## Изоляция PostgreSQL

Профиль `db` автоматически создаёт временный локальный кластер с UTF-8 и свободным
портом, запускает проверки и останавливает/удаляет кластер даже после ошибки.
Для внешнего тестового кластера можно задать `DNDSHARE_TEST_DSN` — postgres URL
с host `127.0.0.1` и родительской БД `dndshare_test_*`. Пользователю нужна
возможность создавать БД. Эта родительская БД не очищается: `internal/testdb`
создаёт отдельную случайно названную БД для каждого теста и удаляет только её.
Go-пакеты могут выполняться параллельно.

`DNDSHARE_TEST_REQUIRED=1` превращает отсутствие DSN в ошибку. Runner включает
этот флаг для DB-профиля, поэтому успешный DB-прогон означает выполненные
интеграционные проверки. Обычный `go test ./...` без DSN явно пропускает их.
Новые HTTP-тесты авторизации и browser smoke используют полную текущую схему из
реальных миграций. Фикстуры feature-тестов содержат только собственные данные;
исторические преобразования данных для их подготовки не запускаются. Изолированные
SQL-проверки отдельных store-методов могут использовать текущий DDL предметных
таблиц и минимальные stubs для несвязанных таблиц; эти фикстуры не подменяют
проверки настоящего HTTP API с полной схемой.

Сценарии истории, применений, переводов, инвентаря и хроники получают отдельную
фикстуру/БД. Они запускаются независимо через поднаборы
`TestCharacterSessionPersistencePostgres`; порядок сценариев не создаёт тестовые данные.

## Проверка эффектов после минификации

Эффекты, зависящие от CSS-префиксов и оптимизации, дополнительно проверяются
узкими файлами проекта production. `tests/navigation/blur-production.spec.js`
проверяет настоящий минифицированный frontend: общий хедер, переход в лист и
создание персонажа, computed стандартный фильтр и обратимый цикл кадров.
Этот файл не входит в dev-проект UI; полный production-набор не запускается
без прямой команды пользователя.

## Браузерные наборы

Общая конфигурация — `frontend/playwright.suite.config.js`; `playwright.config.js`
и прежние feature-конфиги — короткие совместимые обёртки без собственных серверов и настроек:


- `ui`: браузерные компонентные/функциональные сценарии на Vite;
- `maps`: обычные сценарии карт на Vite, один worker для WebGL;
- `production`: мировые карты и загрузки изображений на production build;
- `models`: отдельный диагностический запуск с `DNDSHARE_TEST_MODELS=1`;
- `fullstack`: собранный frontend и настоящий Go API на изолированном PostgreSQL;
  его сервер и URL создаёт Go-тест из профиля `browser`.

Обычные сценарии не зависят от содержимого игнорируемого `models/`. Проверки
с тегом `@local-model` требуют подготовленных файлов, `@gpu` — браузерного GPU
таймера. В диагностическом профиле недоступные ресурсы явно отмечаются как skip;
замеры SwiftShader не считаются измерением аппаратного GPU.
Диагностика `miniaturesBenchmark.spec.js` загружает восемь принятых видов пилота
и три основания из models/; проверяет 40 фигур, полный/LOD режим, тени, поворот
и отсутствие draw calls в покое. Состав и ограничения измерения —
[в отчёте пилота](reports/creature-miniatures-pilot-2026-10-25.md).
`DNDSHARE_TEST_HARDWARE=1` выбирает локальный Chrome (Metal на macOS) и требует
настоящий renderer/GPU timer; SwiftShader не принимается за аппаратный результат.
`DNDSHARE_MINIATURE_ROOT` выбирает подготовленный набор для сравнения до/после.
Диагностика имеет открытое поле и комнату: 170 каменных полов, 28 стен, два
источника с переключаемыми тенями и выделенный жетон. Завершение кадра проверяется
gl.finish/readPixels **только в тесте**, отдельно от асинхронного GPU-профиля.
Метрики содержат backend, разрешение, число кадров, прогрев, mode таймера,
кеш, задержки и отсутствие новых draw calls в покое; rAF не выдаётся за готовый FPS.

Примеры узких запусков из `frontend`:

```bash
npm test -- --run src/features/handbook/pages/ViewHandbook.test.js
npm run test:browser -- --project=maps tests/maps/resilience.spec.js
npm run test:browser -- --project=production tests/global-maps
npm run test:models
```

Runner выбирает свободные порты; ручной браузерный запуск использует 15440/15441.
Серверы запускаются с `strictPort` и без переиспользования постороннего сервера.
У каждого тестового Vite-сервера собственный cacheDir в target/vite-cache,
поэтому параллельные порты и checkout не перезаписывают кеш активного dev-сервера.
`forbidOnly` включён для всех проектов. При ручном запуске JSON сохраняется в каталоге test-results frontend под именем
results.json. Runner сохраняет раздельные отчёты browser/models/fullstack в
каталоге target/test-reports frontend. Пути можно задать через
`DNDSHARE_BROWSER_REPORT` и `DNDSHARE_BROWSER_OUTPUT`.

## Контракты и качество фикстур

Сетевые подмены должны сопоставлять `url.pathname.startsWith('/api/')`, а не
`**/api/**`: широкая маска перехватывает также JS-модули `/src/shared/api/`.
Фикстуры записей реализуют текущий протокол `baseVersion`, `mutationId`, `patches`
и чтение `/changes`; неизвестный формат нельзя заменять старым `version/data`.

SSE-конверты Go и JS сверяются с
`internal/web/testdata/session-live.json`; общий контракт патчей —
`internal/documentpatch/testdata/contract.json`. Уведомления получают данные
`chronicle`, а не прежнюю инвалидацию `journal: true`.

UI-тест проверяет действие и результат: сохранение, запрос, доступность контрола,
смену состояния, сохранность черновика после ошибки. Проверки исходных строк,
имён переменных и точного CSS не заменяют такое поведение. Общий контракт
композиции проверяется у общего компонента, правила предметной области — отдельно
у потребителей. Статические проверки допустимы для архитектурных ограничений,
например DDL-only миграций. Для неизменяемого формата пароля используется
фиксированный независимо вычисленный PBKDF2/SHA1 вектор, а не второй round-trip.
Для SSR-композиции доступен `frontend/tests/unit/renderComponent.js`: он создаёт
отдельное приложение для каждого рендера, принимает slots, plugins и provide.
Pinia и предметные фикстуры создаются внутри теста, без общего состояния между сценариями.
