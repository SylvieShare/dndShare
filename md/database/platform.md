# БД: аккаунты, карты и инфраструктура

Текущие startup-миграции содержат только DDL. Упоминания прежних
нумерованных этапов ниже описывают происхождение уже сохранённых данных;
эти SQL-файлы и преобразования больше не поставляются и не выполняются.
Изменения содержимого выполняются отдельно. [Правила migrator](../database.md).

## Игровые карты

Структура карт включает:

- `battle_map`: UUID, владелец, название, документ JSONB, revision,
  changed_at. Индекс владельца.
- `session_map`: UUID, FK сессии с каскадным удалением, название, независимый
  документ JSONB, runtime state JSONB, revision и changed_at.
  Индекс сессии; UNIQUE(session_id,id).
- `session_map_display`: одна строка на сессию, FK активной сессионной карты,
  visible, камера JSONB и отдельная revision. Составной FK запрещает выбирать
  карту другой сессии. При удалении активной копии одна транзакция сбрасывает
  map_id/visible перед удалением.

Обновления защищены условием `WHERE revision=$expected`; запись увеличивает
revision. Системные пресеты создаются кодом и не требуют seed-строк.
Сессионный `state` также хранит необязательные переопределения видимости
областей и освещения: `areas` и `lighting`. Они меняются через ту же revision,
не затрагивают библиотечный документ и не требуют изменения SQL-схемы;
формат описан в [контракте карт](../features/maps.md#реализация-и-синхронизация).
Библиотечные и сессионные карты хранят только 3D-раскладки и не ссылаются
на storage_image. Подробнее: [игровые карты](../features/maps.md).

`map_model` хранит текущие модели:
UUID версии, коллекцию, source_code, исходное source_name, отдельное name,
номер версии, tile_type, JSONB геометрии и JSONB
asset metadata. Геометрия содержит размеры в клетках, высоту пола, максимальную
высоту, контуры препятствий и теги. Assets описывают source/render/lod/shadow/preview:
S3 object key, SHA-256, byte-size, MIME и имя файла. Ключи содержат хэш файла;
замена байтов под прежней версией не допускается.
Новая покраска регистрируется новым UUID/номером версии и может повторно использовать
source asset. Read API выбирает новую визуальную версию только при совпадении
контракта размещения и хэша исходника; сохранённые документы и их FK не переписываются.
`assets.shadow` является обязательной ролью:
существующие версии получают ссылку на свой LOD. CHECK требует ровно пять ролей
ресурсов. Отдельный GLB для теней хранится в том же S3 по SHA-256; новая теневая
геометрия публикуется новой совместимой версией без изменения остальных assets.
Повторная публикация идемпотентна; проверка хэша актуального LOD защищает от
устаревшего результата подготовки. Изменение покраски может наследовать shadow
совместимой версии. Сохранённые UUID карт остаются прежними.

Логические определения моделей хранятся отдельно:
`map_model_definition.id` — постоянный ключ `sourceCode` с суффиксом
для дополнительных одноимённых вариантов; `map_model.definition_id` — FK всех
версий. Trigger назначает ключ каждому пути регистрации. Определение хранит
revision и JSONB-массив default_lights, включая необязательные настройки пламени effect.
`map_model_transition` хранит направленные
переходы между определениями и enum действий, уникальные по источнику/цели/действию.
Метаданные новой версии и поведение записываются атомарно с проверкой обеих
ревизий. Встроенные Light в документах имеют builtinKey и anchor экземпляра;
источники восстанавливаются из определения, включённость остаётся на карте.
Подробнее: [переходы моделей и встроенный свет](../features/maps-model-behaviour.md).

Общий `code` хранится в определениях
моделей. Это код семейства, не уникальный ID элемента: UD-010 и UD-010-OPEN
имеют разные определения и общий UD-door. Начальная разметка объединяет
завершающие номера, размеры каркасов, состояния и компоненты графа переходов;
символы пола получают общее семейство. Код редактируется для определения,
виден у всех его версий и не меняет UUID/ресурсы/параметры размещения. Новые
определения получают код через trigger из пака и исходного имени.

`geometry.textureDetail` описывает детализацию текстур:
`basic` (поверхностная проработка) или `detailed` (детальная). CHECK требует одно
из этих значений. По хэшу render детальными отмечены подготовленные версии
UD-006, UD-009 и UD-010, остальные записи получают basic. Это характеристика
оформления версии, поэтому она не ограничивает совместимость размещения.
Read API показывает значение выбранных визуальных assets; MCP сохраняет
историческое значение конкретной версии.

`hasDecor` является явным флагом модели
со столами, скамьёй, колодцами, рычагом, камнями, трубами и щупальцами.
Меняется только классификация встроенной обстановки: UUID/версии, ресурсы,
геометрия, canStand и placementPoints сохраняются. Старые версии исправляются
вместе с текущими; новая обработка определяет наполнение отдельно от дерева,
воды и других материалов поверхности.

Тип и форма представлены одним `tile_type`:
`floor`, `wall-straight`, `wall-angle`, `wall-tee`, `wall-cross`, `wall-corner`,
`wall-custom`, `stairs`, `frame`, `prop`. Известные прежние формы стен переносятся
в соответствующий тип; остальные стены становятся `wall-custom`. Поля
`terrain_type`/`wall_layout` удалены; пак определяется `collection`. Индекс
фильтра теперь покрывает `(collection,tile_type)`. `wallMode` и `wallMask`
по-прежнему описывают геометрию стыков независимо от категории. Миграция сохраняет
UUID, версии, assets, размещения и ссылки FK существующих карт.

Категории стен различают окончания (`wall-end`)
от наружных углов (`wall-corner`, например UD-096) и добавляет `wall-diagonal`
(UD-097/106). Стены с исходным именем Corner/Angle/Diagonal переносятся в свою
категорию; оставшиеся wall-custom становятся обычными прямыми стенами. Старого
wall-custom больше нет в CHECK/API. UUID, assets, геометрия стыков и документы
карт сохраняются. Тот же выбор формы используется импортёром.

Документ карты хранит солнце (enabled,
angle=225, elevation=45) и пустой lights. Параметры хранятся в JSONB документа;
каждый источник содержит id/name/kind/color, x/y/elevation/height, intensity/radius,
enabled/showMarker/shadows/flicker, offset, необязательные anchor {kind,id} и areaId. API
ограничивает число источников 32 и включённых локальных источников с тенями — двумя;
проверяет диапазоны, цвет и ссылки на модели/область. Сохранение использует обычную
revision карты; добавление в сессию копирует параметры. Публичный снимок скрывает
названия источников. Документ поддерживает
`lightingEnabled=false` и каждому сохранённому источнику `showMarker=true`,
сохраняя остальные параметры и порядок источников. Новые карты также начинают
с выключенным режимом освещения; сферы новых источников включены. Оба флага
сохраняются при копировании карты в сессию.

Массив `areas` принадлежит JSONB-документам battle_map/session_map. Каждая
область хранит id, name, color, hidden, fog, tileIds и objectIds. Go API проверяет
имена, RGB-цвет, существование элементов и единственное членство экземпляров;
изменения сохраняются с обычной revision карты. Копия для сессии сохраняет области
исходной карты. API принимает `#RRGGBB`, при отсутствии цвета задаёт `#8b5cf6`.
Фокус области — transient-состояние редактора, в БД он не записывается.

`fog` по умолчанию false и независим от `hidden` и сессионного state.fog. Он
включает покрытие тайлов области, скрывает её объекты и отключает связанный свет
в рендере, сохраняя сами объекты и enabled/параметры источников. Выключение флага
восстанавливает прежнее отображение. Значение участвует в снимке сессии,
автосохранении, undo/redo и подписи WebP-превью; новая SQL-колонка не нужна.

Геометрия модели хранит hasDecor/canStand/hidden
и placementPoints в geometry, категории bridge/passage/column и тип object.
Декор больше не является tile_type. Три UD-модели скрыты из нового каталога
без удаления FK сохранённых карт. Явная публикация модели сохраняет
высоты опорных точек по декодированной геометрии, совпадающему исходнику и
контракту размещения. Объекты используют modelId из того же registry и placement
{tileId,point}; FK map-model таблиц фиксируют как плитки, так и модели объектов.
Точки общие с персонажами. Высота сцены вычисляется из этажа опорного тайла
и elevation точки с поправкой mountDepth.

Библиотечные и сессионные карты используют только `kind=tiles`. Теги
хранятся массивом строк в документе. Startup не удаляет другие документы,
не объединяет JSON и не выключает трансляции; подготовка данных выполняется
отдельно от структурных определений.

Карты используют только текущий 3D-формат. Системные пресеты строятся в коде;
startup не удаляет старые документы и не выключает трансляции. Модельные файлы
относятся к системному storage; статистика дедуплицирует asset keys между
версиями, личный лимит пользователя они не расходуют.

## Пользователи

`users`, `role`, `users_role`, `users_session`. Актуальные роли:
`ADMIN`, `HANDBOOK_ADMIN`. Роли редактора шаблонов нет, потому что шаблоны
находятся в коде. `users.source_version_id` — обязательный FK глобально
выбранной игроком редакции. Система определяется через `source_version → source`
и не дублируется в `users`. Trigger назначает DND5e 2014 новому аккаунту до первого выбора, если эта
редакция уже подготовлена в каталоге. Существующие аккаунты startup не меняет.
`users_session.created_at` ограничивает серверную сессию 30 днями; просроченные
строки удаляются при старте. Смена пароля атомарно отзывает прежние сессии, а
самостоятельная смена создаёт новый token текущему браузеру.

## Музыка и storage

`music_track`, `music_album`, `music_tag` и link tables хранят metadata и
порядок. Личные альбомы/треки имеют `owner_user_id`; у системных
`is_system=true`, владелец отсутствует, а `system_key` обеспечивает
стабильную идентичность отдельно импортируемых данных каталога. CHECK constraints не дают совмещать
системный признак с владельцем. Личное и системное аудио лежит в object
storage; системные объекты используют стабильный префикс `system-music/v1/`.
Системный трек может участвовать в `music_album_track` личного альбома и в
`music_track_tag` с личным тегом. При чтении API такие связи фильтруются по
владельцу альбома или тега; связи с системными альбомами остаются общими.
Изображения справочника, персонажей и сессий используют `storage_image`/S3, SVG
справочника — `svg_storage`. `session_image_catalog` описывает категории и
порядок системных обложек отдельно для `story` и `npc`; главы, локации и NPC
хранят единый обязательный `image_id`, а сценарий может вместо собственного
изображения наследовать его по `location_id`. Системные JPEG загружаются под
стабильными ключами `system-session-images/v1/{story|npc}/`.

Личные `storage_image` хранят `user_id`, `file_size`, `file_name` и `mime_type`;
такие же upload metadata есть у пользовательских `svg_storage`, а музыка
использует эквивалентный `owner_user_id` и `file_size`. Встроенные и системные
объекты имеют `NULL`-владельца и не входят в личную статистику. Размеры DB-backed bytes/SVG заполняются отдельной операцией с данными; размер старых S3-объектов без
локальных bytes лениво уточняет account API и сохраняет обратно. Частичные
индексы по владельцу и времени обеспечивают список последних загрузок без
сканирования системного каталога.

Административная статистика агрегирует эти же `file_size` по всем владельцам и
системным объектам. Для `storage_image` учитываются только активные строки с S3
key или DB-backed bytes, для `music_track` — системный признак, для
`svg_storage` — фактические DB-backed записи. Поэтому внешняя иллюстрация по URL
не выдаётся за занятое место, а неизвестный размер показывается отдельным
счётчиком и не приравнивается к нулю.

## Удалённые таблицы page reports

Исторические таблицы `error_report`, `error_report_message` и
`error_report_automation_lock` сохранены без изменений. Приложение не читает
и не изменяет их; отправки, очереди и обработки репортов больше нет. Старые
роли `ERROR_REPORT_AUTO_APPROVE` и `ERROR_REPORT_REVIEWER` могут оставаться
в сохранённых назначениях, но больше не предоставляют возможностей. Панель
локальных ошибок консоли доступна только `ADMIN`.

## Админ-джобы

`job_run` хранит историю фоновых операций. В реестре остаются регулярный
пересчёт counters и импорт бестиария; преобразования форматов данных выполняются отдельно через MCP или явно
запускаемые операции. Startup schema содержит только структурный DDL.

## Прогресс обучения

`dndshare.user_tutorial` хранит прогресс с PK
`(user_id, flow_id, source_key, device)`, полями `revision`, `status`, `updated_at`
и каскадным удалением вместе с пользователем. Прогресс листа разделён по редакции,
прогресс сессии — по системе и роли. Upsert изменяет только один ключ и не
понижает версию; повторный запуск настраивается удалением выбранного результата.
Подробности: [обучение](../features/tutorials.md).

`schema.go` встраивает все SQL-файлы из `internal/store/schema/` и
упорядочивает их по имени. Проверка манифеста сверяет файлы с registry,
структурным DDL и неизменяемым checksum базы. Данные механик оружия
и предметов хранятся отдельно и не входят в миграции.

Метаданные магических предметов содержат
`initial_charges` и `confirmed_uses`. Публичному предмету 134 задаются начальные
1к8+1 зарядов и подтверждаемое списание после гибели цели. Описание, основа,
бонус и чужие зависимости сохраняются; данные экземпляров не изменяются.
Состояние запаса хранится в `params.magic.max_use`/`remaining`; поиск ссылок
на ресурсы распознаёт `initial_charges` как основной ресурс предмета.

Метаданные типа 19 поддерживают начальные запасы
отдельных ресурсов, условие активности зависимости, ожидание подтверждаемого
применения в рассветах и связь переброса с применением. Публичному Клинку удачи
(171) подключаются два ресурса, бонус спасбросков, удача и желание. Описание,
основа и существующие чужие зависимости сохраняются, экземпляры не меняются.
Состояние хранится в `params.magic.resource_maxima`, `resource_counts` и
`use_cooldowns` по ключам ресурсов/применений. Явная подготовка данных не должна дублировать
зависимости; интеграционный тест сверяет итоговую схему с JSON-снимком.
