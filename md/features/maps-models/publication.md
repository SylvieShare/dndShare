# Модели карт: идентичность, упаковка и публикация

Статус: обязательные правила для указанной области.

## Идентификатор, код группы и название

У логического тайла или объекта постоянная идентичность и двуязычные подписи:

| Поле | Как заполнять | Пример |
| --- | --- | --- |
| `id` | Постоянный уникальный ID конкретного варианта; не менять при новой обработке ресурсов. | `UD-010`, `UD-010-OPEN` |
| `code` | Код раздела каталога: объединяет связанные формы одного назначения/стиля и задаёт порядок разделов. | `MED-ground`, `MED-bar` |
| `variantCode` | Код взаимозаменяемых вариантов внутри раздела. Разные направления, углы, высоты и занимаемые клетки — разные семейства. Пусто — без семейства вариантов. | `MED-ground-straight`, `MED-bar-angle` |
| `name` / `nameEn` | Русское и английское название конкретной модели, без ID в подписи. В интерфейсе показывается `name`. | `Прямой край грунта 1` / `Ground Straight 1` |
| `groupName` / `groupNameEn` | Русское и английское название раздела, общие для `collection`/`code`. | `Тропинки` / `Paths`, `Барные стойки` / `Bars` |
| `category` | Категория каталога независимо от геометрической формы `tileType`. | `wall`, `water`, `railway`, `floor` |

Одинаковый `code` создаёт один заголовок раздела. Все модели имеют обычные
отдельные карточки без раскрытия; одинаковый непустой `variantCode` ставит
варианты рядом. Ground Straight 1/2 — одно семейство; Ground Corner и прямой
участок — разные семейства раздела Ground. Обычный, высокий и угловой Bar —
разные семейства раздела Bar; Bath Empty/Water — одно семейство. Свободные модели
и модели с предметами могут и должны оставаться в одном разделе, если это один
стиль/назначение. Наполнение `hasDecor` не образует группу само по себе.
Косметика и состояния могут быть вариантами; разные формы/размеры — разные
семейства. Постоянные ID и переходы не меняются при исправлении классификации.

Оба языка заполнять явно: читаемый русский без английских слов из файла,
английский без технических префиксов, при этом `sourceName` не переводить.
Уточнять форму, состояние, материал или наполнение; Angle — внутренний угол,
Corner — наружный. Число варианта сохранять, если оно различает модели.
Названия групп не выводить из общего префикса имён: они хранятся один раз в
`map_model_group`. При переименовании группы меняются подписи всех её моделей.

`category`: `floor`, `wall`, `water`, `railway`, `stairs`, `frame`, `bridge`,
`passage`, `column`, `object`, `creature-base`. Все формы стен относятся к `wall`; форма остаётся
в `tileType`/стыках. Вода, речные участки и водопады — `water`, железнодорожные
пути — `railway`; мосты остаются `bridge`. Стол, ванна или фонтан сами по себе
не относятся к воде только из-за наполнения. Категория не меняет геометрию,
стыки, возможность встать или набор источников света.

Примеры: двери UD-010/UD-010-OPEN относятся к разделу UD-passages и семейству
UD-door; UD-016/017 — раздел UD-ground, семейство UD-ground-stones;
UD-048–053 — раздел UD-ground, семейство UD-ground-symbol.
В админском справочнике отдельно редактируются «Код группы» и «Код вариантов».
Через MCP использовать map_tile_model_grouping_update с models:[{definitionId,
expectedCode, expectedVariantCode, code, variantCode}]: читать текущие значения
перед записью, передавать оба ожидаемых кода, включая пустую строку. Пакет до
1000 определений атомарен, устаревшее значение отменяет весь пакет; повтор уже
установленной пары идемпотентен. UUID, ресурсы, геометрия, свет и переходы сохраняются.
map_tile_model_group_update меняет только раздел, сохраняя семейство вариантов;
также требует expectedVariantCode. Запросы без нового ожидаемого поля отклоняются.

Для новой регистрации можно передать code и variantCode вместе с метаданными.
Повторная публикация геометрии всегда сохраняет текущую классификацию из БД.
Рецепт, который явно меняет классификацию, должен содержать обе разметки:
groupCode (раздел) и variantCode. Исторический groupCode без variantCode не имеет
права перезаписывать проверенную разметку реестра. apply-majestic-group.mjs
сохраняет уже назначенную пару при обработке только геометрии; первичная классификация задаётся явной парой, а изменение подтверждается свежим MCP-чтением.
Первоначальный проверяемый план формирует scripts/maps/model-grouping-plan.mjs;
явное применение — scripts/maps/apply-model-grouping.py. Это отдельная операция
с данными, не startup-миграция. Не перегенерировать план поверх ручных правок:
использовать сохранённый план с ожидаемыми исходными значениями.

Названия/категории менять через `map_tile_model_catalogue_update`: отдельные
массивы `models` и `groups` до 1000 записей каждый, полный набор ожидаемых
значений из свежего чтения. Запись атомарна, повтор целевого состояния
идемпотентен; ресурсы, геометрия, code/variantCode, hasDecor, свет и переходы
не записываются. План перевода готовит `scripts/maps/model-catalogue-plan.mjs`,
явное применение — `scripts/maps/apply-model-catalogue.py`. Это операция с
данными, не startup-DML. Сохранить исходный снимок, план и результат; не
пересоздавать исходные ожидания поверх ручных изменений. Новая модель требует
оба языка модели/группы и категорию. Повторная публикация ресурсов сохраняет
переводы и категорию из реестра; `currentModel` переносит их из свежего снимка.

У каждого тайла/объекта одна текущая запись без истории и поля version.
HTTP-каталог разделяет логический id и постоянный технический uuid. Карты и
сессии сохраняют UUID модели; её обновление применяется к любому размещению.
В MCP-пакете id — тот же UUID, definitionId — постоянный текстовый ID;
sourceCode/sourceName сохраняют происхождение. При повторной обработке читать
свежий реестр и сохранять UUID, definitionId, code, variantCode, sourceName и collection.
Новый UUID назначается только новой модели. Не создавать новый UUID при покраске,
оптимизации, исправлении геометрии, теней или превью. Файлы в S3 по-прежнему
content-addressed: изменённые байты получают новый ключ/хеш; запись модели
переключается на актуальные assets. Старые карты используют эту же запись.

Значок лампочки относится к встроенным источникам из шаблона модели, а не
к свету, добавленному вручную на карту.

## Упаковка и превью

Последовательность для новой геометрии: упрощение → UV → повторное запекание
albedo/normal/ORM → сжатие текстур → Meshopt → проверки конечных файлов.
При перекраске использовать сохранённую геометрию и UV. GLB содержит встроенные
ресурсы; положение узлов и масштаб сохраняются.

KTX2 применяется в поддерживающих его рецептах и проверенном загрузчике:
albedo — ETC1S в sRGB, normal/ORM — UASTC с Zstd в linear, с mipmaps.
Если ETC1S даёт цветные блоки на ровной поверхности, рецепт может выбрать
UASTC+Zstd для albedo, сохранив sRGB и mipmaps. Сравнить с PNG и двумя
бюджетами ETC1S; измерить прибавку веса. Пример — внутренняя отделка LC-060.
В Majestic `renderColourEncoding` и `lodColourEncoding` выбирают `etc1s`
или `uastc` отдельно для каждой детализации; по умолчанию остаётся ETC1S.
Проверять цвет после декодирования на физических участках: у MH-164 ETC1S
окрашивал серую верхушку камня в цвет воды, а UASTC сохраняет её исходный цвет.
Normal сохраняет RGB XYZ; после уменьшения векторы нормализуются. Metallic
задаётся материалом: нулевое значение MH-001 относится к траве, а железо требует
собственного значения. Размеры карт выбираются по модели и версии детализации.
Если объект содержит пламя или светящуюся поверхность, запекать отдельную
emissive-карту и сжимать её как цветовую карту sRGB. Проверять, что свечение
остаётся только на размеченной поверхности после упаковки; пример —
[лагерь MH-031](../majestic-highlands.md). Lost Cave также передаёт отдельный
Emissive-атлас через prepare-cave-ktx: UASTC sRGB с mipmaps,
цветовое разрешение выбранного бюджета. Chromium-проверка требует
загруженную карту свечения у рецептов с torch.emission;
[LC-079](../lost-cave-mine.md) проверен дополнительно на физических участках
пламени и соседних несветящихся материалов.
Сжатые текстуры проверяются после декодирования и в реальном браузере;
локальное PNG-превью служит дополнительной проверкой.

Упаковка формирует catalogue.json с пятью ролями и файлы по SHA-256.
При повторной упаковке package-masonry проверяет байты существующего
SHA-файла: жёсткая ссылка на рабочий GLB могла измениться при новом запекании.
Несовпадающий файл заменяется проверенными текущими байтами до публикации.
Для новой геометрии shadow создаётся из принятого LOD до публикации. При
перекраске с неизменённой геометрией и LOD разрешено повторно использовать
проверенный отдельный shadow. Пакет Majestic строит его автоматически через
[shadow_model.mjs](../../../scripts/maps/shadow_model.mjs).

Создать полное превью, показывающее габарит со свесами. Для проверки материалов
сделать дополнительные виды спереди, сверху и с обратной стороны, при
необходимости — крупные планы. Диагностические снимки остаются локально;
каталог получает полное WebP-превью модели.
Для коридора, открытого с запада, `preview-model-revisions.py --west --review`
показывает внутренний поток между боковыми стенами, сохраняя полный габарит.

Фон каждого публикуемого превью **обязательно прозрачный**. Не запекать фон,
сетку, плоскость или подписи в изображение; фон карточки задаёт интерфейс.
Все публичные Blender-рендереры используют film_transparent=True и PNG RGBA.
В preview-model-revisions.py прозрачность включена всегда; --transparent
сохраняет отдельный transparent-preview.png вместо preview.png. Освещение
world сохраняется. Кэшированные непрозрачные картинки перерендериваются.
Камера рассчитывает масштаб по проекции полного габарита и оставляет запас
по краям; крупные элементы и свесы не обрезаются. Для обратного вида и вида сверху
масштаб пересчитывается отдельно: длинный бордюр не должен обрезаться после поворота камеры. Для измерения
точек нового верхнего вида `probe-model-surface.py --view top --fit-from top`
использует такое же кадрирование; прежние варианты `--fit-from` сохраняются. Если нужно воспроизвести прежнее вертикальное
кадрирование, --camera-shift-y задаёт сдвиг кадра без изменения модели и света.
Обычные превью сохраняются отдельно и не перезаписываются.

Для замены только превью использовать
[package-preview.mjs](../../../scripts/maps/package-preview.mjs): параметры
--collection, --code, --source-name, --snapshot, --preview, --reference-glb,
--output. Скрипт проверяет совпадение SHA активного render, наличие прозрачных
и непрозрачных пикселей, сохраняет WebP alpha с alphaQuality=100 и создаёт
совместимую ревизию. Остальные четыре ресурса и вся разметка переиспользуются.
Проверить manifest с исходным реестром и публиковать обычным MCP-загрузчиком;
он загружает только новый preview. Проверять сглаживание, отсутствие обрезки,
прозрачность четырёх углов и сохранность альфа-канала после WebP-сжатия.

Для пакетной замены превью подготовить актуальный inventory.json с текущими
моделями и локальными файлами по SHA-256. prepare-transparent-previews.mjs
декодирует активный render (включая KTX2) в временный GLB для Blender,
render-transparent-catalogue.py рендерит ограниченные возобновляемые партии,
package-transparent-catalogue.mjs проверяет рамку/alpha и собирает WebP.
upload-transparent-previews.mjs загружает только новые превью напрямую в S3
через MCP и вызывает map_tile_model_register_preview. Инструмент проверяет
ожидаемый render SHA и обновляет текущую модель, сохраняя четыре остальных
ресурса и разметку; повтор идемпотентен. Изменившаяся во время подготовки модель
попадает в changed.json: получить свежий реестр, перегенерировать её превью и
повторить публикацию. Уже прозрачные актуальные превью пропускаются.

## Публикация через MCP

### Перенос огненных моделей других коллекций

`prepare-fire-base.mjs CODE` переводит принятые UD-036, UD-037, LC-079 и MH-031
на [пламя источников](../maps-light-effects.md). Входы сохраняются в
models/collections/COLLECTION/light-effects/CODE/before с актуальным model
из MCP и GLB, совпадающими по SHA. Каждый код обрабатывается отдельно;
следующий — после подтверждённой публикации текущего.

`fire_light_domains.mjs` повторно использует измеренную разметку покраски:
torchPartAt и поле сравнения с UD-038, исходные контуры и глубину шахтного
факела, сравнение лагеря с SHA-привязанным MH-032. Координаты UD/LC — миллиметры
подготовленного тела; у MH восстанавливается исходный центр STL.
`stripMeasuredFlames` удаляет выбранные треугольники и сохраняет все оставшиеся
атрибуты точно. После Meshopt проверяются fingerprint треугольников с учётом
циклического поворота индексов и побитовая идентичность изображений корпуса.
Исторические нативные QA-хэши остаются у исходных файлов в before.

Затем `preview-light-base.mjs CODE` декодирует KTX2 только для копий Blender,
добавляет статичный образец runtime-пламени, готовит варианты on/off.
`validate-light-shadow.mjs CODE` проверяет свободное пространство вокруг
источника и сохранённую твёрдую опору. `package-light-base.mjs CODE` собирает
пять ролей с неизменным source, `audit-light-base.mjs DIRECTORY` считает
фактические геометрию и текстуры для браузерной проверки.
Публикация ресурсов и добавление effect сохраняют все прочие поля свежих
метаданных, defaultLights и переходов; завершение подтверждается MCP-чтениями.

При полной повторной обработке этих моделей применять fireLightDomain и
stripMeasuredFlames после покраски и до финальных shadow и превью.
proceduralFire и параметры встроенного огня закреплены в рецептах;
публиковать корпус со скульптурным пламенем при таком рецепте нельзя.

### Ресурсы пакета

Водная анимация использует маску принятых PBR-каналов с порогом roughness
из рецепта конкретной модели; перепубликация ресурсов не требуется.
Измеренные поверхности могут дополнительно содержать `_WATER`, как MT1-032.
`water_animation_profiles.mjs` определяет профиль, а
`review-water-animation.mjs` проверяет текущие render/LOD до назначения
через MCP. Метка water служит кандидатом, пустые ёмкости исключаются.
Охват каталога, подготовка точной маски фонтана и проверки описаны
в [анимации воды](../maps-water-animation.md).


```bash
model_assets_dir=models/collections/majestic-highlands/optimized-upload/MH-001
go run ./cmd/map-model-upload -assets "$model_assets_dir" -workers 1
```

Для записи требуется MCP_WRITE_ENABLED на сервере. Клиент получает подписанные
PUT URL, отправляет байты непосредственно в S3, подтверждает формат, размер и
SHA-256 и регистрирует модель. Зарегистрированные UUID и известные ресурсы
переиспользуются; изменённая модель сохраняет UUID и заменяет текущие assets.
Токен и подписанные ссылки не выводятся в журнал.

Новые пакеты передают shadow явно. При обновлении без shadow и с тем же LOD сервер сохраняет текущий shadow,
а при первой регистрации использует LOD. Для новой геометрии подготовить отдельный
компактный shadow GLB.
