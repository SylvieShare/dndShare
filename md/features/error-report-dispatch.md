# Доставка багрепортов в локальный Codex

Один постоянный чат проекта получает отдельное сообщение о новом репорте.
События создаются также при одобрении, ответе человека, повторном открытии,
подтверждении изменения и восстановлении истёкшего claim. Права и статусы
[репортов](error-reports.md) сохраняются: неодобренные заявки не исправляются.

## Сервер

`error_report_event` — транзакционный журнал без описаний и снимков. Триггеры
добавляют строку вместе с изменением репорта/сообщением; rollback отменяет обе
записи. Startup-миграция `017_error_report_events.sql` содержит только DDL.
Существующие репорты не преобразуются и не удаляются.

Внутренний id журнала выделяется при записи. Публичный `delivery_id` назначается
только уже закоммиченным строкам, в отдельной короткой транзакции публикации под
advisory lock. Бизнес-транзакции не берут эту блокировку. Это исключает пропуск
позднего commit с меньшим внутренним id при продвижении курсора.

`GET /mcp/error-report-events?after=N` требует тот же bearer, что MCP. Если query
не указан, используется Last-Event-ID. Ответ — SSE с `id`, `event:error-report`
и JSON `{id,reportId,kind,approved,status,createdAt}`. Порядок — delivery id.
`approved` и `status` отражают текущую запись. События удаляются вместе с репортом;
пропуски id допустимы. Сервер проверяет журнал каждую секунду, heartbeat — каждые
15 секунд, write deadline продлевается. Nginx не буферизует поток.

`error_report_get(id)` читает актуальную одобренную заявку, включая IN_PROGRESS
и завершённые состояния. Это позволяет чату перечитать собственный claim после
возобновления. Неодобренные записи и изображения остаются недоступными через MCP.

## Компьютер

`scripts/error-reports/dispatcher.py` держит исходящее HTTPS-соединение; входящий
порт компьютера не открывается. Обрыв вызывает переподключение с задержкой до
15 секунд. Курсор и квитанции доставок хранятся в локальной SQLite с WAL/FULL.
При старте существующая готовая очередь также попадает в чат. Bootstrap и live
created одного reportId используют общий ключ, повтор SSE не создаёт сообщение.

Уведомление содержит id, вид события и фиксированную инструкцию. Описание
репорта не становится аргументом команды. Codex вызывается через subprocess
без shell; подтверждение проверяется по точным messageId и threadId в квитанции
`codex queue`. Подтверждена постановка в очередь, а не завершение анализа.
Разбор требует запущенного Codex и доступной авторизации. Его ограничения/ошибки
видны в самом чате. На этом компьютере доставка проверена через desktop-чат.

Один worker удерживает файловую блокировку процесса. После перезапуска он
продолжает с сохранённого курсора. Доставка имеет семантику как минимум один раз:
при аварии между принятием CLI и локальным commit возможно повторное уведомление.
Сообщение содержит стабильный ключ, а агент проверяет текущий статус, lease и
claim и не выполняет завершённую работу повторно. Токены, lease и описания не
попадают в лог обработчика.

## Установка и управление

Из чистой актуальной копии:

~~~powershell
.\scripts\error-reports\install.ps1 -ThreadId CHAT_UUID -ProjectDirectory C:\Projects\dndshare -TokenEnvFile C:\Projects\dndshare\.env -Start
~~~

Без Start установка подготавливает конфигурацию и отключённую задачу до
подтверждённого запуска. Файлы устанавливаются в LocalAppData/dndshare/report-dispatch.
Настройки содержат только пути, URL и id чата. MCP_AUTH_TOKEN читается из заданного
локального env-файла, не копируется в командную строку или репозиторий. Redirect
с авторизованного HTTP-запроса запрещён.

Задача Windows `DnDShare-Report-Chat` запускается при входе текущего пользователя,
без повышенных прав и окна. Если служба задач недоступна по правам, используется
пользовательский Startup shortcut. Worker можно остановить через Stop-ScheduledTask
с этим именем. Состояние соединения — state/health.json, журнал — state/worker.log
с ротацией. Секреты не выводятся при диагностике.

## Клиент агента

`reportctl.py --config CONFIG ACTION` использует штатный HTTP MCP. Команды:

- list — готовая очередь; get ID — актуальная заявка; image ID — локальный файл
  снимка для просмотра через инструмент изображений;
- acquire, renew, status, release — управление общим lease; capability хранится
  только в локальном файле, stdout содержит безопасную квитанцию;
- claim ID... — атомарный пакет;
- title/question/serious ID с text-file — заголовок, конкретный вопрос или запрос
  решения; resolve ID с text-file и commit — результат выпущенного исправления.

Текстовые аргументы берутся из UTF-8-файла. Агент не подставляет пользовательский
текст в shell. После вопроса/результата соответствующий id убирается из локального
списка claims; в конце обработки обязателен release.
