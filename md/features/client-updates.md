# Версии и обновления веб-интерфейса

Источник версий — [release/versions.json](../../release/versions.json).
Бэкенд, frontend и Android имеют независимые semver и числовые build.
Git SHA и sourceHash показывают точную сборку. Номер frontend build используется
для сравнения обновлений; строки версий не сравниваются лексикографически.

Текстовые runtime-входы, включая go.mod и go.sum, нормализуются к LF перед
расчётом sourceHash. Одинаковые Windows/Linux checkout дают одинаковые отпечатки;
бинарные медиа сохраняют исходные байты.

## Повышение версий

До коммита исходников выполнить:

~~~powershell
node scripts/release/versions.mjs --bump
node scripts/release/versions.mjs --check
~~~

Первый вызов сравнивает отпечатки источников и повышает patch/build изменившихся
компонентов. Android-отпечаток входит в frontend: смена нативного runtime также
создаёт новую целевую веб-сборку. Тесты и Markdown не являются runtime-входами.
Для контролируемого повторного выпуска есть --force=frontend.
Проверка релиза отклоняет исходники без версии и движение номеров назад.
Повышение происходит до фиксации кода; release не меняет чистый commit.

Версия backend не повышается из-за простого встраивания новых HTML/JS/CSS.
Go-бинарь всё равно пересобирается, а его commitSha меняется. Изменение Android
требует APK; совместимая веб-сборка может поступить через OTA.

## Блок в меню

BuildVersions располагается над аккаунтом и сворачиванием панели, в desktop
и выдвижном меню. Он показывает выполняющуюся версию frontend и полученную
версию backend. Свёрнутая панель открывает подробности через Info.
Подробности содержат build, SHA, версию оболочки и источник UI: APK/OTA.
Без сети backend помечен как последний известный; frontend берётся из самой сборки.

## Упаковка и подпись

Vite встраивает __DNDSHARE_BUILD__ и build-info.json. Нативная задача использует
тот же готовый build-info, чтобы версия и sourceHash не разошлись с HTML/JS.
pack-frontend.mjs создаёт ZIP, файловую опись SHA-256 и подписанный envelope.
Пакет содержит только веб-ресурсы; .gz/.br и нативные исполняемые файлы исключены.
ZIP ограничен 64 МиБ, распакованные данные — 128 МиБ, 2048 файлами.

Подпись SHA256withECDSA/P-256 создаётся локальным release-процессом.
Открытый ключ [frontend-ota-public.pem](../../release/frontend-ota-public.pem)
входит в Git и APK. Закрытый ключ хранится вне репозитория:
по умолчанию в профиле пользователя .codex/secrets/dndshare-frontend-ota-private.pem;
DNDSHARE_FRONTEND_SIGNING_KEY задаёт другой путь. Release прекращается при
отсутствии ключа или несовпадении пары. Ключ не попадает в архив или приложение.
Его резервную копию следует хранить как секрет; смена доверенного ключа требует APK.

## HTTP-контракт

- GET /api/build-info — backend version/build/commitSha/apiContract и metadata frontend.
- GET /api/frontend-updates/latest — envelope с base64 payload и DER-подписью.
- GET /api/frontend-updates/{sha256}.zip — неизменяемый архив по хэшу.

Metadata endpoints имеют Cache-Control:no-store, архив — immutable.
Они публичны, не требуют сессии и не зависят от доступности БД.
Frontend передаёт X-DnDShare-Client-Api; неподдерживаемый контракт даёт
426 CLIENT_UPDATE_REQUIRED до выполнения операции. Metadata остаётся доступна
старому клиенту, чтобы он мог определить нужное обновление.

## Совместимость

NativeRuntime — отпечаток Java, Android-ресурсов, manifest, конфигурации,
зависимостей Capacitor, генератора runtime и открытого ключа.
contracts.api и contracts.data входят в отпечаток. Несовместимая смена API,
SQLite/JSON/outbox-формата требует повышения контракта и новой оболочки.
Дополнительные совместимые поля документов не требуют смены контракта.
Применяется только пакет с точным совпадением nativeRuntime и обоих контрактов.

## Нативный жизненный цикл

FrontendUpdates работает независимо от JS. Он проверяет релиз при запуске,
возвращении и раз в минуту активности. HTTPS ограничен origin dndshare.ru;
редиректы не используются. Перед записью проверяется подпись, затем размер,
хэш ZIP, пути, полнота и SHA каждого файла. Установка идёт через staging и rename.

Данные находятся в files/frontend-updates отдельно от SQLite, медиа и очереди.
Ресурсы переключаются через API Capacitor, origin/cookies сохраняются.
Новый пакет выбирается при холодном запуске или безопасном возвращении из фона.
Редактор, сессия, создание, открытая форма, picker, загрузка и мутация блокируют
автоматическое переключение. В подробностях есть явный перезапуск с flush очереди.

Vue подтверждает готовность после открытия локальной базы, mount и router.ready.
Nonce, build и sourceHash связывают подтверждение с загруженной сборкой.
Без подтверждения за 30 секунд видимого времени выполняется откат.
Незавершённый запуск после смерти процесса также откатывается.
Ошибочный build/sourceHash записывается и не скачивается заново по кругу.
Встроенная версия APK остаётся резервом; сохраняется предыдущая рабочая OTA.
Ошибки загрузки или хранилища не удаляют пользовательские данные.

Откат фронта не откатывает БД или серверные изменения. Для исправленного
или возвращённого кода публикуется новый возрастающий frontend build.

## Проверки

Node проверяет подпись/опись/детерминированность ZIP и правила версий.
Go — публичную metadata без БД и блокировку несовместимого API-клиента.
Browser — версии в трёх форматах и в свёрнутой панели.
FrontendUpdatesTest проверяет реальный WebView из подписанного пакета,
сохранность SQLite, rollback по таймауту и прерванному процессу, повреждённую
подпись/ZIP, несовместимый runtime, zip traversal и отказ записи.
