# Производительность frontend

Статус: действующий контракт. Числа отдельных запусков находятся в отчётах.

## Состав production-сборки

[Vite-конфигурация](../frontend/vite.config.js) отключает разделение страниц и CSS:
приложение поставляется одним JS и одним CSS. Динамические импорты исходников
сохраняются, но переходы по приложению не требуют загрузки чанков старого релиза.
Three.js и общий renderer переиспользуются; модели и изображения загружаются
отдельно по необходимости. Basis transcoder и BVH worker — разрешённые отдельные
ресурсы, они не являются чанками навигации.

## Проверка состава и измерение размера

[check-bundle.mjs](../frontend/scripts/check-bundle.mjs) проверяет состав manifest,
один JS/CSS приложения, Basis decoder, BVH worker и отсутствие дополнительных
runtime-чанков. Размеры initial/total JS/CSS, декодера и geometry worker
выводятся в gzip-байтах для информации; ограничений размера нет.

`npm run build` из frontend создаёт production-сборку и выполняет проверку.
Скрипт считает gzip стандартным `gzipSync`; серверный sidecar с уровнем 9 не
подменяет эту метрику. Предупреждение Vite о 500 KB не отключается.
`npm test` проверяет, что большие корректные пакеты проходят проверку, а лишние
чанки и отсутствие обязательных worker/decoder-ресурсов по-прежнему дают ошибку.

При разборе роста размера сравнить чистую базовую и изменённую сборки на
одинаковых зависимостях, проверить import graph и manifest. Результат с исходным
commit, методом и окружением записать в датированный отчёт.

## Runtime и графические измерения

[Нагрузка карт](features/maps-performance.md) описывает CPU/GPU по этапам,
renderer и ограничения аппаратных/программных замеров. Frame interval не равен
времени GPU; SwiftShader не является показателем FPS пользовательского GPU.
Браузерные измерения выполняют на стабильной копии кода, без Vite HMR.
