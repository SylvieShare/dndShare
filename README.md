# dndShare

D&D-мастерская: персонажи, справочник, игровые сессии, карты и музыка.
Runtime — Go, Vue 3, PostgreSQL и S3; production поставляется одним Go-бинарём
с вшитым frontend. Версии зависимостей задают [go.mod](go.mod) и
[package.json](frontend/package.json).

Этот README — единственный источник общих проектных инструкций.
AGENTS.md и CLAUDE.md только направляют сюда. Тематические правила обязательны
при работе в своей области; отчёты и планы не заменяют текущий контракт.

## Начало работы в новом чате

1. Прочитать этот файл и проверить `git status --short` и текущую ветку.
2. Определить файлы своей задачи и посторонние изменения. Не удалять, не
   откатывать и не включать чужую работу в коммит. Для новой задачи с кодом использовать отдельную ветку/worktree на диске C;
   один чат владеет одной рабочей копией. Не делить незакоммиченные изменения
   и staging area между параллельными задачами.
3. В локальном MCP ContextShare вызвать `select_worktree` с абсолютным путём
   рабочей копии задачи. Передавать возвращённый `project_id` во все следующие
   вызовы. Проверить `workspace` в ответе, затем вызвать `get_project_overview`
   и найти [маршрут задачи](.contextshare/wiki/README.md#с-чего-начать) и контракт фичи.
4. Выполнить работу, обновить описания через ContextShare и пройти соответствующую
   строку [матрицы проверок](.contextshare/wiki/testing.md#матрица-проверок).

## Документация и wiki

ContextShare — интерфейс чтения и изменения вики. Данные хранятся в Git
в `.contextshare/wiki/`, вложения лежат рядом с документами. Изменяй страницы и
типизированные связи через MCP или CLI ContextShare. Сверяй Git diff и коммить
поправку контракта вместе с изменением кода.

Локальное подключение Codex к выбранному worktree:

```powershell
# Собрать contextshare.exe из репозитория ContextShare.
go build -o C:/Tools/contextshare.exe .
codex mcp add contextshare-local -- C:/Tools/contextshare.exe local --project C:/Projects/dndshare
```

`--project` задаёт начальную копию репозитория. В MCP выбирай фактический worktree
через `select_worktree`. `list_worktrees` показывает доступные копии. В ответах
`workspace` указывает путь, ветку, commit и локальные изменения. Исходники инструмента
и форматы CLI описаны в [репозитории ContextShare](https://github.com/SylvieShare/contextshare).
Скрипты записи журналов используют `contextshare` из PATH или явный
`CONTEXTSHARE_BIN` с путём к исполняемому файлу.

| Действие | Команды MCP |
| --- | --- |
| Начать работу | `get_usage_guide`, `list_worktrees`, `select_worktree`, `get_project_overview` |
| Найти знания | `search`, `list_sections`, `get_section`, `list_nodes`, `get_node`, `get_related_nodes` |
| Прочитать страницу или вложение | `get_wiki_document`, `get_wiki_attachment` |
| Добавить или обновить страницу | `write_wiki_document`. Для существующей страницы передай SHA-256 из чтения. |
| Удалить страницу или изменить связь | `delete_wiki_document`, `set_wiki_link` |
| Добавить или заменить вложение | `write_wiki_attachment` |
| Проверить вики | `validate_wiki` |
| Вести очередь | `list_requests`, `get_request`, `add_requests`, `prepare_request`, `claim_request` |

Поиск по умолчанию показывает действующие материалы в выбранной рабочей копии.
Для отчётов передавай `status=historical` или `status=all`. `current` описывает
материал внутри указанной ревизии и не подтверждает актуальность другой ветки.

- [Оглавление и маршруты задач](.contextshare/wiki/README.md) — выбор области и проверок.
- [Сопровождение wiki](.contextshare/wiki/documentation.md) — владельцы тем, переносы и ссылки.
- Текущее поведение живёт в `.contextshare/wiki/features/`, HTTP-контракты — в `.contextshare/wiki/api/`,
  хранение — в `.contextshare/wiki/database/`. История и измерения — в `.contextshare/wiki/reports/`, предложения —
  в `plans/`. При изменении поведения соответствующие описания обновляются
  в том же коммите; если текст менять не нужно, его всё равно проверяют.
- Устаревший API или промежуточный формат не оставляют в текущем контракте.
  Источник изменяемых версий и лимитов — конфигурация или код, указанные на странице.

## Общие ограничения

- Runtime читает текущую схему и формат. Изменение формата сопровождается явным
  преобразованием данных и переключением всех producer/consumer; старые поля,
  aliases, fallback-ветки и временные jobs удаляются.
- Startup SQL содержит только DDL. Справочник, медиа и преобразования данных
  меняют через MCP или отдельно запускаемые операции; правила — [БД](.contextshare/wiki/database.md).
- Общий веб-UI принадлежит `@sylvieshare/share-ui`. Перед локальным компонентом
  сверить [каталог](.contextshare/wiki/frontend/components.md). Не копировать примитивы и не
  обходить недостаток API базовым CSS. Разрешённый межрепозиторный процесс —
  [сопровождение share-ui](.contextshare/wiki/frontend/share-ui.md). Общие Android-примитивы
  принадлежат [Android design system](native/androidApp/DESIGN_SYSTEM.md); API и игровые
  модели остаются в приложении.
- Интерфейс учитывает [анимации и reduced motion](.contextshare/wiki/frontend.md#анимации-и-переходы).
- Веб и Android развивают единый визуальный интерфейс. Изменение общей композиции,
  размеров, элементов управления или оформления выполняется синхронно в обоих
  клиентах небольшими законченными шагами. Клиенты выпускаются по готовности.
  Три формата проверяются при изменении адаптивной раскладки.
  Общие размеры и типографика задаются в [design/tokens.json](design/tokens.json).
  При изменении общей композиции оба клиента сверяются на одинаковых данных;
  различия отображения допускаются по отдельной договорённости с пользователем,
  которая фиксируется в [реестре исключений](design/visual-exceptions.json).
  Правила и границы —
  [адаптивный дизайн](.contextshare/wiki/frontend/responsive-design.md).
- По мере работы над UI переводить затронутые участки веба и Android в общий
  безрамочный стиль: группировка отступами, типографикой и поверхностями,
  с обводками для значимых интерактивных состояний. Допускается согласованная
  корректировка палитры. Направление и последовательность —
  [план безрамочного интерфейса](plans/frameless-interface.md).
- При изменениях листа и сессии проверить влияние на [обучение](.contextshare/wiki/features/tutorials.md).
  Цели, действия и тексты обновляются при изменении их контракта; сохранённый
  completed/dismissed прогресс не сбрасывается и автоматически не повторяется.
- Загрузка данных не блокирует навигацию и готовые части интерфейса. Новые и
  изменяемые экраны используют скелетоны страницы, вкладки или конкретной записи;
  фоновое обновление сохраняет готовое содержимое, ошибка завершает ожидание
  и предлагает повтор. Правила — [состояния загрузки](.contextshare/wiki/loading-states.md).
- Соблюдать [границы исходных файлов](.contextshare/wiki/file-size-rules.md). Страницы остаются
  тонкими, логика имеет явного владельца и один публичный контракт.

## Структура проекта

Нативный Android-клиент находится в [native/](native/README.md).
`native/androidApp` содержит экраны, данные и синхронизацию;
`native/androidApp/.../ui/designsystem` — отдельный пакет общего оформления внутри приложения. Используется только тёмная тема.
Точность визуала и удобство важнее обязательной нативности каждого элемента.
Для сложных эффектов допускаются SVG, шейдеры, кэшированная растеризация или
локальный web-renderer, если это лучше воспроизводит согласованный веб-референс
и проходит проверки производительности/жестов. Перед переносом изучают
исходную реализацию веб-компонента, а не воспроизводят её по памяти.
Минимальная версия — Android 8.0 (API 26). Обновление подключённого телефона
по команде пользователя выполняет `scripts/native/install.ps1` с сохранением
данных; подключение и выбор устройства описаны в инструкции native.
Адаптивная вёрстка — обязательный принцип проекта: телефон, средние/малые
планшеты и foldable, большие окна/планшеты и desktop. Формат определяется
доступным окном; веб и Android используют одинаковые телефонную, планшетную
и desktop-композиции. Samsung Z Fold8 — целевое
устройство проверки раскрытия, поворота и изменения размера окна.
Подробности — [нативный клиент](.contextshare/wiki/features/native-client.md).

`main.go` запускает приложение; `internal/config`, `internal/store`,
`internal/storage`, `internal/web` владеют конфигурацией, БД, S3 и HTTP/MCP.
`frontend/` содержит Vue-приложение, `internal/assets/` — встроенную сборку.
`deploy/` отвечает за выпуск, `scripts/` — за проверки и операции сопровождения.
Подробности — [архитектура](.contextshare/wiki/architecture.md).

## Локальная разработка

Frontend: из `frontend/` выполнить `npm install`, затем `npm run dev`.
Backend: из корня загрузить локальный `.env` и выполнить `go run .`.
Vite использует порт 5173 и проксирует API/MCP на 8080.
`npm run build` в `frontend/` создаёт `frontend/target/dist`; deploy встраивает
его в `internal/assets/dist`. Правила окружения — [деплой](.contextshare/wiki/deploy.md).

Обычная работа на Windows использует Node, Go и Android SDK напрямую.
Проверки с изолированными Go API и PostgreSQL запускаются через WSL.
Шаги короткого цикла задаёт [UI-процесс](.contextshare/wiki/frontend/ui-workflow.md).

## Проверки

**Полный набор тестов запускается только по прямой команде пользователя.**
Это относится к `ui.py verify --full`, общим browser/`all` профилям и
неограниченным прогонам web unit. Обычная правка и выпуск сами по себе
не разрешают полный прогон. По умолчанию проверяются затронутые модули,
сценарии и форматы окна, на которые влияет правка.

Обязательный набор выбирается по [матрице](.contextshare/wiki/testing.md#матрица-проверок).
Быстрый путь — `scripts/ui.py focus` с выбранными файлами или модулем.
Широкие `test.py fast/browser/all` профили и `ui.py verify` требуют `--full`,
который допустим только после прямой команды пользователя.
После правки документации вызывай `validate_wiki`. В автоматических проверках
структуру и ссылки также проверяет `python3 scripts/check-wiki.py --strict`.
Изменение проверяющего инструмента дополнительно требует его unit-тестов.

## Деплой завершённого изменения

Пользователь разрешил отправлять завершённые изменения в `origin/main` и
запускать штатный deploy без повторного согласования, если не попросил иначе.
Это разрешение не отменяет ограничения среды и автоматическую проверку действий.
При её отказе сначала проверить причину и фактический scope; если требуется
прямое подтверждение, сообщить причину и запросить его для конкретного коммита.

1. Выполнить [матрицу проверок](.contextshare/wiki/testing.md#матрица-проверок) по риску изменения.
2. Явно добавить только файлы задачи: `git add -- <пути>`; проверить
   `git diff --cached --stat` и содержимое diff. Не использовать `git add -A`
   в общем или грязном checkout.
3. Создать содержательный коммит по-русски. При общей staging area использовать
   явный список путей и для коммита. Отправить завершённый коммит в `origin/main`.
4. Для изменения серверного runtime собрать и выпустить чистую копию именно этого commit
   через [штатный выпуск](.contextshare/wiki/deploy.md#чистая-release-копия). Записать абсолютный путь release-копии, SHA и её
   пустой `git status`; проверить readiness с тем же SHA.

Изменения только Markdown и инструментов разработки или выпуска коммитятся и отправляются
в main после своих проверок; production-бинарь ради них не пересобирается.
Порядок выпуска и работа с параллельными изменениями — [runbook](.contextshare/wiki/deploy.md).

Android-клиент выпускается отдельным APK после
проверок из [native/README.md](native/README.md), с записью исходного commit.
Изменение только Kotlin/UI клиента не требует перезапуска Go-сервера;
изменения его API, схемы или встроенного сайта проходят серверный deploy выше.
Визуальную приёмку выполняет пользователь. Для косметики достаточно проверить
затронутое состояние, отдельный отчёт необязателен.
